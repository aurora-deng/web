# PostgreSQL 迁移规则

当前业务版本要求 001–024 都存在。024 是当前功能所需的最后一份迁移，不是永久冻结线。只修改代码组织、界面或测试时，保持原表结构和版本。

本地复现已在一次性 PostgreSQL 从空库应用 001–024，并验证应用启动与重启后的数据读取。[复现记录](../ops/validation/reproduce.md#这次的验证记录)

## 增加迁移

1. 在[迁移目录](../../backend/application/storage/postgres/migrations)追加下一编号，如 `025_feature_name.sql`。已经发布的 SQL 不改写、不复用编号。先核对 `phase11_schema_migrations`，不要以文件总数代替版本检查。
2. 明确锁、执行时间、回填与索引成本。可事务化的变更，把 DDL、必要的数据变更和版本登记放在同一事务；需要单独执行的操作提供可重跑、可观察的迁移步骤。
3. 在新空库按顺序应用，再用隔离的旧版本备份演练升级，验证数据、权限和事务；同时更新运行时版本校验、健康版本信息、测试及文档。不得在启动时隐式修改业务库。
4. 日常库升级前先备份并验证备份可读。使用[日常启动说明](../ops/runtime/function3-runtime.md)中的显式步骤，只有获得部署授权后才执行。

优先采用旧代码仍能读取的扩展迁移：先增加结构，再回填和切换，最后在另一个版本处理删除。代码回退前先确认兼容性；遇到破坏性变更时，不能靠切回旧二进制撤销数据库变化，要按预演过的恢复方案操作。空库复现见[干净环境指南](../ops/validation/reproduce.md)，它不会连接原库。
