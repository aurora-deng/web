# NEBULA 可观测性实战

## 第一部分 · 我自己做实验

你已有 Reactor、协程、HTTP 和数据库基础。下面按六次实验展开，每次约 40–60 分钟。先完成当课的自检，再开始下一课。

### 第 1 课 · 区分服务状态和证据状态

- **概念**　`live` 像检查门店是否开门，`ready` 检查是否能接单，指标抓取检查记账员是否拿到了流水。
- **动手**　按[启动指南](setup.md)打开隔离实例，核对存活、就绪、抓取与历史保存。切到一次没有聊天流量的窗口，看 ACK 目标显示「没有请求」或覆盖不足。对照[状态与信号边界](architecture.md#信号字典)。
- **自检**　业务请求正常，但监控凭据过期。哪一个状态会失败？看见过去的零错误能判断当前健康吗？

### 第 2 课 · 从四个黄金信号定位异常

- **概念**　用流量、错误、延迟、饱和度回答「来了多少、失败多少、要等多久、哪里排队」。P99 相当于从短到长排列后取接近第 99% 的位置，经典直方图只知道每段的数量，需要在桶内估计。
- **动手**　在同一压测窗口对照 QPS、会话 P99、执行器队列和 PostgreSQL 连接池。到 Explore 看一次原始桶，记下总样本和桶上界。对照[直方图查询示例](explore-and-connect.md#explore-查-p99-和延迟桶)。
- **自检**　只有 12 个请求时，一条慢请求如何改变 P99？为什么不可用「总 P99 − 排队 P99」推导执行 P99？

### 第 3 课 · 从告警量化用户影响

- **概念**　SLI 是你实际统计的合格比例，SLO 是期望比例。99% 目标允许每百次有一次不合格，这个比例就是错误预算。最近观测如果每百次有 6 次不合格，预算消耗速度就是 6×。
- **动手**　打开「服务目标与采集质量」。读出总样本、未达标数、首尾采样时间和窗口覆盖。对照 1 分钟与 5 分钟的快速判定，再看 5 分钟与 30 分钟的缓慢判定。固定窗口后用 API 返回的 `events` 和 `bad` 手算。
- **自检**　1 分钟内错误率跳高，5 分钟仍低于阈值，页面应怎样判定？当业务返回 429 时，当前 HTTP 目标和用户实际感受可能有什么差别？

```python
total, bad = 175, 12
target = 0.99
sli = (total - bad) / total
burn_rate = (bad / total) / (1 - target)
print(f"达标率 {sli:.2%}，预算消耗速度 {burn_rate:.2f}×")
```

这组数来自本轮隔离演练。另取短窗分母才能复核快速判定。6 小时滚动预算需要连续的六小时证据。示例阈值用于练习，生产目标应由业务请求契约和用户影响定义。[真实验收记录](validation.md#服务目标与采集质量的真实验证)

### 第 4 课 · 从指标跳到一条请求

- **动手**　从 HTTP 目标选择「查找同窗 HTTP 5xx Trace」。先在入口 span 看状态属性，再沿父子关系到 ChatService、仓储和 libpq。延迟目标可以跳同窗慢 Trace。「函数与内核剖析」可直接选中实际的函数 span。
- **对照**　在同一窗口查进程、线程、调度和网络，必要时载入 Callgrind、DHAT、strace 报告。用客户端 RTT、服务端阶段、数据库 span 和 CPU 样本分别解释各自的测量边界。
- **自检**　Trace 上的数据库调用墙钟高、线程 CPU 低，可能在等什么？用哪项新证据区分连接池等待、数据库内锁和调度？

### 第 5 课 · 做一次可比较的故障演练

- **动手**　先记录基线和预测。在独立库做 PostgreSQL 锁等待和请求取消，核对业务 5xx、采集状态及缓慢恢复。实际入口见[分项验证](setup.md#分项验证)。用同一负载复跑一次，记忆中的「感觉变快」要用可比的 A/A 和 A/B 证据确认。
- **记录**　抄录二进制摘要、配置、并发、夹具、UTC 窗口、样本量和错误。贴一条 Trace，写下一个能被下一轮实验推翻的假设。使用[历史验收记录](validation.md)核对长期观察的边界。
- **自检**　恢复后长窗口还残留错误，短窗口已回落，如何区分正在发生的故障和过去的影响？

### 第 6 课 · 接入新信号并证明采到了

- **动手**　选 DAG、Agent 或设备。按[扩展样例](explore-and-connect.md#验证扩展生产者接通)发送、重复发送并回读。再用[系统拓扑和组件索引](architecture.md)标出采集队列、持久化、查询和页面各自失败时的症状。
- **产出**　交付一张调用路径图、一个指标口径表、一个故障报告和能重跑的命令。报告写清哪些数据来自隔离真请求，哪些来自模拟生产者。
- **自检**　追踪 ID 为何适合查明细，却不适合作为 Prometheus 标签？应用显示导出成功后，还要核对哪一步才能证明浏览器读得到？

```text
统计题用 Python，线程和生命周期用 C++。先让我预测，再用真实隔离实验验证。
围绕同一实例和时间窗核对指标、Trace、资源和实验。标明样本量、缺测、模拟和推断。
用一个自检题确认我能复述，收到我的命令后再进入下一步。
```
