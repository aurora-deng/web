## 3. 三轮同配置性能

环境使用同一虚拟机、编译器与Release配置；Reactor=2、HTTP Worker=4、WS Worker=4、业务DB Worker/Pool=4。新版本另有Function3四连接池和投递两连接池，属于新增功能开销，未隐藏。Broker始终存在，只有当前版本使用事件转运。没有同时运行编译或模型推理。

`/fast` 使用已有wrk：两线程、64连接，预热3秒、测量10秒。混合负载为四客户端Worker、1200操作、四条驻留SSE，HTTP会话查询50%、历史20%、WS聊天30%，每轮360个持久ACK样本。订阅就绪用真实消息回环单独确认，启动恢复时间不混进稳态样本。

## 4. 性能定位与实际改进

1. 原发布器最多等待250ms轮询，已改为提交后通知与唤醒代次，轮询只作恢复兜底。
2. 删除每个Function3事务中重复的两条SET，连接构造时仍保留5秒语句、2秒锁等待期限。
3. 发布领取/确认最多四条不同aggregate，减少提交次数；45秒租约覆盖四次8秒SDK等待。同会话顺序不变。
4. SDK FIFO内部无限重排已用显式补丁终止；最多16个未完成SDK发送，持久Outbox独立管理重试。
5. 投递读取独立连接池。观测中普通业务池等待由数百次降至接近零，但尾延迟仍高，不能继续把主要瓶颈归咎于连接池。
6. `ChatOutboxWriter` 把旧事件索引与新持久队列合并进原业务事务，删除中间移交的两次提交；提交后通知不捕获已销毁Runtime，回滚不通知。新旧记录原子性已由真实PG契约验证。
7. 已对私有PG开启WAL I/O计时并做同负载对照，结束后恢复两个设置为off。结果如下，确认新增持久链路带来更多同步写入；不能把所有P99变化仅归因于单次磁盘延迟。

| 单轮I/O诊断 | 基线 | 当前 |
|---|---:|---:|
| WAL写入/刷盘次数 | 702 | 1308 |
| WAL写入字节 | 6823936 | 12369920 |
| WAL写入累计时间ms | 55.822 | 106.551 |
| WAL刷盘累计时间ms | 493.679 | 906.328 |
| 本轮ACK P99 ms | 45.046 | 44.210 |
| 业务错误 | 0 | 0 |

当前WAL刷盘次数约为1.86倍，累计时间约1.84倍，而单次平均刷盘时间接近。它支持“持久处理次数增加”的定位，不能据此声称每次刷盘都变慢。此轮额外开启计时、包含创建夹具和订阅就绪；只用于诊断，不能用这一轮接近的P99覆盖上面的三轮未达标结论。Broker进程I/O还包含启动和后台工作，不能直接解释为每条业务消息的成本。

剩余重点是发布/消费事务合并、服务端排队和CPU调度的进一步隔离测量。当前实现仍未达到ACK门槛，这项没有被标记完成。

## 5. 本轮修正的运行问题

- 冷试听和冷模型试装超过默认HTTP期限，改为有界后台任务与状态查询。
- WebM可能没有原始duration；限时解码后以实际WAV时长判断，不能直接放行N/A。
- TTS资源文件名包含空格，摘要清单按固定摘要前缀解析。
- 子进程隔离服务器fd，限制内存、CPU、文件、日志输出和执行时间，停机取消并回收；父进程异常退出也不遗留无人管理的子进程。
- 吊销先移除广播目录并撤销WS新任务准入，再尝试关闭帧；队列满也不能继续授权。
- 隔离PG契约/容量库与真实HTTP库分开，避免重置测试ID与旧文件目录冲突。
- 命名空间启动等待完成，只进入与当前不同的namespace；退出时stat/cmdline竞争不会被误判为可操作的未知进程。测试账号后缀遵守用户名长度约束。
- 90%磁盘保护正常触发时没有调高阈值或降低刷盘保证。只清理本轮可重建对象、保留相同SHA的已验证二进制，并整理私有测试库空间；模型、正式数据和原有安装保留。
