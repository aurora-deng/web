# 09 · 火焰图 Flame Graph（详细讲义）

> Benchmark：知道「慢了 / QPS 掉了」。  
> Metrics：知道「队列堆了 / CPU 满了 / 连接涨了」。  
> **火焰图**：回答最后一问——**CPU 时间到底花在哪个函数调用栈上？**

没有它，你只能猜：「是不是 Parser？是不是 memcpy？」

---

## 我对火焰图的理解（笔记）

**核心定义（自己的话）：**

> **火焰图 = 把 CPU 采样统计画成图，看时间主要耗在哪些函数调用栈上；横向越宽越吃 CPU。**

它解决的问题：

```text
已经知道「CPU 满了、很慢」
但不知道是 Parser？memcpy？日志？锁？
→ 看火焰图宽度
```

**易错点：** 火焰图**不是时间轴**，左边不是「先执行」。  
**用法：** 和 Benchmark/Metrics 闭环——发现慢 → 看状态 → 采样 → 改 → 再测。  
**态度：** 异常时再采，不必一直开着。

## 1. 火焰图本质（人话）

程序跑着的时候，工具**每隔一小段时间拍一张「现在卡在哪一层函数」的快照**。  
拍成千上万次后统计：

```text
哪些调用栈出现得最频繁 ≈ 哪些地方最吃 CPU
```

可视化成火焰图：

- **横向越宽** → 占用 CPU 比例越大（越「热」）  
- **纵向越高** → 调用栈越深  
- **不是时间轴**：左边不是「先发生」，右边不是「后发生」——这是新人最容易误会的点。

示意：

```text
              memcpy
             ██████
          HttpParser::parse
        ████████████
       Buffer::append
     ████████████████
    EventLoop::loop
  ████████████████████
```

一眼：`memcpy` 很宽 → 拷贝是热点。

---

## 2. 什么时候需要采？

典型：

```text
wrk → QPS 低、P99 高
Metrics/top → CPU 100%，队列不堆
→ 说明在「算」而不是「等」
→ 采火焰图看算在哪
```

生产上通常**不一直开** perf（有开销）；Metrics/告警说「P99 突然坏了」再采那一段。

## 3. 工具链（Linux）

```text
perf record -g
    → perf script
    → stackcollapse-perf.pl
    → flamegraph.pl
    → flame.svg（浏览器打开）
```

### 编译要求

必须带符号，否则全是 `??`：

```text
推荐：RelWithDebInfo（-O2 且 -g）
不要：strip 光光的纯 Release 又要读图
```

### 采样命令示例

```bash
# 终端 A：压测
wrk -t8 -c1000 -d60s http://127.0.0.1:8080/

# 终端 B：对服务器 PID 采约 30 秒
perf record -F 99 -p <PID> -g -- sleep 30
perf report          # 先看文本版热点也行

perf script > out.perf
./stackcollapse-perf.pl out.perf > out.folded
./flamegraph.pl out.folded > flame.svg
```

`-F 99`：大约每秒采样 99 次——够用且不太搅乱程序。

## 4. 结合你的 WebServer：四种典型读图

| 火焰图很宽的东西 | 人话结论 | 优化方向 |
|------------------|----------|----------|
| `malloc` / `string` 扩容 / `memcpy` | 疯狂分配与拷贝 | `reserve`、少临时 string、对象池、更好的 Buffer |
| `HttpParser::parse` | 解析本身热 | 状态机、少拷贝、`string_view`（注意生命周期） |
| `fwrite` / Logger | 同步日志拖死 | 异步日志、降级日志级别 |
| `pthread_mutex_lock` / `futex` | 锁竞争 | 队列分片、减少共享、无锁/原子结构 |

闭环写法：

```text
图上 malloc 40% → 改 Buffer
→ 再 Benchmark：QPS 30000→45000
→ 写入性能报告
```

这才是完整性能工程，不是「看过一眼 SVG」。

---

## 5. 和 Metrics 的配合

```text
Metrics：10:05 P99 从 5ms 飙到 200ms
  → 只在 10:05 附近 perf
  → 火焰图显示 malloc 50%
  → 定点优化
```

比「随便找个空闲时间采一张」有用得多。

## 6. 本仓态度

火焰图是**定位武器**，收尾**不强制**每人都采一张。  
怀疑 CPU 热点、要写优化报告时再上。细节协议也可对照 [../../../performance/BENCHMARK.md](../../../performance/BENCHMARK.md)。

## 7. 本章小结

1. 火焰图 = CPU 热点的调用栈可视化；看**宽度**。  
2. 用 `perf` + FlameGraph；二进制要有符号。  
3. 和 Benchmark/Metrics 闭环：发现慢 → 看状态 → 采热点 → 改 → 再测。  
4. 不要当日常常开监控。
