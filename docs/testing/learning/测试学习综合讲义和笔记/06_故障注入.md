# 06 · 故障注入（Fault Injection）（详细讲义）

> 前面测的是「正常世界」：客户端正常、网络正常、机器正常。  
> **故障注入** = **主动制造故障**，看系统在「异常世界」还能不能稳住。  
> 高性能后端真正关心：异常时会不会泄漏、拖死、崩掉。

---

## 我对故障注入的理解（笔记）

**核心定义（自己的话）：**

> **故障注入 = 主动把环境或客户端弄「坏」（延迟、丢包、慢发、CPU 打满、突然断开），观察服务器是否仍稳定、是否泄漏、是否该超时就超时。**

和别的层别混：

| 名称 | 我的区分 |
|------|----------|
| 黑盒畸形请求 | 发错误 HTTP 内容 |
| Fuzz | 自动砸组件输入（多是 Parser） |
| **故障注入** | 整机运行时叠**坏网络/坏节奏/坏资源** |

典型担心（自己的话）：

> 慢客户端一直占着连接，会不会把 fd/内存耗光？——所以要测超时和释放。

本仓：思想要懂；成体系故障平台不是收尾必做。

---

## 1. 和 Fuzz、黑盒差在哪？（先别混名）

| 名称 | 在干什么 | 例子 |
|------|----------|------|
| 黑盒畸形请求 | 发错误 HTTP，看协议处理 | `GETTTTT`、CL+TE 冲突 |
| **Fuzz** | 自动砸**组件输入**（多是 Parser） | 随机字节进 `parse` |
| **故障注入** | 给**运行中的整机**叠坏环境/坏客户端节奏 | 网延迟 100ms、慢发、CPU 打满 |

本仓有 Fuzz；**成体系的故障注入平台未做**——见 [../CLOSED_LOOP_MAP.md](../CLOSED_LOOP_MAP.md)。讲义仍要学思想。

---

## 2. 为什么 Benchmark 之后还要故障注入？

普通压测很「理想」：

```text
客户端飞快发完请求，飞快收响应
```

现实里手机网络可能：

```text
发了 "GET /"
  卡住 30 秒
再发后面的字节
```

若服务器傻等、不超时：

```text
每个慢连接占着：fd + 内存 + Buffer
× 10000
→ 资源耗尽
```

这就是 **Slowloris** 一类问题。压测「快乐流量」测不出来。

## 3. 故障分四类（地图）

| 类 | 模拟什么 | 常见工具 |
|----|----------|----------|
| 网络故障 | 延迟、丢包、限速 | Linux `tc netem` |
| 资源故障 | CPU/内存打满、fd 上限 | `stress-ng`、`ulimit` |
| 应用/客户端异常 | 慢发、断开、超大请求 | Python 脚本 |
| 依赖故障 | DB/Redis 超时 | 本阶段可暂缓 |

## 4. 网络延迟 / 丢包（tc）

本机 wrk → `127.0.0.1` 走 **lo（回环）**：

```bash
# 加 100ms 延迟
sudo tc qdisc add dev lo root netem delay 100ms

wrk -t4 -c100 -d30s http://127.0.0.1:8080/

# 丢包 10%（示例）
# sudo tc qdisc add dev lo root netem loss 10%

# 一定要恢复！
sudo tc qdisc del dev lo root
```

### 你该观察什么？

- P99 随延迟上升：**通常正常**（物理上就慢了）。  
- 不正常：连接数/内存**只涨不跌**、最后崩溃 → **超时或背压有洞**。

## 5. 慢客户端（强烈建议理解）

```python
import socket, time

sock = socket.create_connection(("127.0.0.1", 8080))
sock.send(b"GET ")
time.sleep(5)
sock.send(b"/ HTTP/1.1\r\n")
time.sleep(5)
sock.send(b"Host: x\r\n\r\n")
```

含义：TCP 还在，但 HTTP 迟迟不完整。  
服务器应：有限等待 → **超时关闭** → 释放资源。

检查泄漏直觉：

```bash
ls /proc/<pid>/fd | wc -l
```

开很多慢连接后若 fd 数持续爬升不回落 → 危险。

这依赖你的 **Timer / 空闲超时**（第三阶段就有 TimerWheel 思想）。

---

## 6. 客户端异常断开

```python
sock.sendall(request)
sock.close()  # 不等响应，直接走
```

服务器侧常见事件：`EPOLLHUP` / `EPOLLERR` / read 返回 0。  
必须释放：Channel、Connection、Buffer，**不能只 close(fd) 却漏删对象**（内存泄漏），更不能回调打到已释放对象（UAF → 配 ASan）。

---

## 7. 大请求 / 慢速占连接

```python
# 超大 Header：应 400/413 或断开，禁止无界涨到 GB
payload = b"X: " + b"A" * 1_000_000 + b"\r\n\r\n"
```

这与黑盒「正文上限」相邻，但故障注入更强调：**资源被恶意耗尽时的策略**。

---

## 8. CPU / 内存压力

```bash
stress-ng --cpu 4 --timeout 60s
stress-ng --vm 2 --vm-bytes 80% --timeout 60s
```

同时 wrk：看延迟恶化多少、是否崩溃、错误率。  
模拟「机器上还有别的服务抢 CPU」的生产现实。

## 9. 最强组合：故障 × Sanitizer × 压测

| 场景 | 组合 | 容易挖出 |
|------|------|----------|
| 1 | ASan + wrk + 随机断开 | Connection UAF |
| 2 | TSan + 并发 + 随机 close | data race |
| 3 | tc 延迟 + Timer | 超时逻辑错误 |

---

## 10. 本章小结

1. 故障注入测的是**异常环境下的稳定性**，不是 QPS 数字本身。  
2. 慢客户端 / 超时 / 断开是自研服务器必考题。  
3. 与 Sanitizer 组合，才能把「泄漏/UAF」坐实。  
4. 本仓现阶段：**知道位置即可**；不要为了凑名词强行搭混沌平台。
