# 04 · Benchmark 压测（详细讲义）

> 黑盒问：**能不能正确处理请求？**  
> Benchmark 问：**大量请求下，还能不能又快又稳？**  
> 高性能后端真正要学会的不是「会敲 wrk」，而是：**建基线 → 做对比实验 → 解释瓶颈**。

---

## 我对 Benchmark 的理解（笔记）

**核心定义（自己的话）：**

> **Benchmark = 在大量请求/高并发下，测量服务器还能不能保持性能，并用数字说话。**

黑盒关心「对不对」；压测关心：

```text
QPS 能到多少？
延迟（尤其 P99）多长？
错误率是不是接近 0？
```

**自己要记住的三点：**

1. **先建基线，再优化**——「感觉快了」不算；要和同一环境、同一命令对比。  
2. **QPS 不是唯一真理**——P99 很高的高吞吐，生产可能不可用。  
3. **压测是发现问题的入口**，不是终点；还要靠 CPU / Metrics / 火焰图解释「为什么」。

和黑盒的一句话对比：

> 黑盒：功能对不对；Benchmark：机器性能怎么样。

---

## 1. 为什么需要压测？

黑盒：

```text
1 个客户端 → 200 OK  → 「能用」
```

生产：

```text
成千上万客户端同时来 → 延迟飙升 / 错误 / CPU 打满 → 「不能用」
```

压测就是在实验室里**提前制造这个世界**。

---

## 2. 核心指标：每个词都讲清楚

### 2.1 QPS（Queries Per Second）

**每秒处理多少个请求。**

```text
Requests/sec: 50000
→ 大概每秒 5 万次 HTTP 请求
```

QPS 高 ≠ 一定好（见下文 P99）。

### 2.2 Latency（延迟）

**从发出请求到收到响应花了多久。**

用户体感主要看这个：点一下按钮，是 2ms 还是 2s。

### 2.3 P50 / P95 / P99（分位延迟）——后端最重要的延迟看法

把很多次请求的耗时从小到大排序：

```text
P50：一半请求比它快（中位数）
P95：95% 请求比它快
P99：99% 请求比它快（尾巴，最能暴露「偶发很慢」）
```

**为什么平均值会骗人？**

```text
999 次：1ms
1 次：10 秒
平均看起来还行，但那个倒霉用户等了 10 秒
```

所以工业看 **P99**（有时还看 P999）。

### 2.4 Error Rate（错误率）

连接重置、超时、5xx……  
**错误率不是 0 的「高 QPS」不能当可持续能力。**

### 2.5 选型直觉

| 方案 | QPS | P99 |
|------|-----|-----|
| A | 50000 | 500ms |
| B | 40000 | 5ms |

生产往往选 **B**：略慢一点的吞吐，换稳定尾巴延迟。

## 3. 工具：wrk（工业常用）

```bash
# 示例安装
# sudo apt install wrk

wrk -t4 -c100 -d30s http://127.0.0.1:8080/
```

| 参数 | 人话 |
|------|------|
| `-t4` | 开 4 个压测线程去制造负载 |
| `-c100` | 同时保持约 100 条 TCP 连接 |
| `-d30s` | 连续砸 30 秒（太短会受握手、冷启动干扰） |

本仓：`scripts/gen_report.sh`、`benchmark.sh`；更严的可复现协议见 [../../../performance/BENCHMARK.md](../../../performance/BENCHMARK.md)。

也有人用 `ab`（ApacheBench），思想相同：固定并发与总请求数，看吞吐和延迟。

## 4. Benchmark-1：先建「性能基线」（Baseline）

### 4.1 什么叫基线？

某一固定版本 + 固定配置 + 固定命令，测出的一组数字，例如：

```text
版本 v1.0
Release 构建
SubReactor=4, worker=8, Keep-Alive 开
wrk -t4 -c100 -d30s
→ QPS 25000, P99 8ms, Error 0
```

这就是 **Baseline**。  
以后你改 Buffer / 线程数，都要和它对拍：「是真快了 28%，还是感觉快了」。

### 4.2 环境必须固定（否则数字不可比）

写进报告（教学文件可叫 `performance.md`）：

- 硬件：CPU 核数、内存、是否虚拟机  
- OS  
- 编译器版本、**Release / -O2**（Debug `-O0` 可能差一个数量级，**不能当性能结论**）  
- 服务器参数：端口、Reactor 数、worker 数、是否 Keep-Alive  

### 4.3 阶梯压测（不要一上来一万连接）

```bash
# ① 单连接：看单线程极限、排除并发干扰
wrk -t1 -c1 -d30s http://127.0.0.1:8080/

# ② 普通并发
wrk -t4 -c100 -d30s http://127.0.0.1:8080/

# ③ 高并发（可加长到 60s）
wrk -t8 -c1000 -d60s http://127.0.0.1:8080/
```

记录表：

| 配置 | QPS | P50 | P99 | Error | 备注 |
|------|-----|-----|-----|-------|------|
| t1 c1 | | | | | |
| t4 c100 | | | | | |
| t8 c1000 | | | | | |

### 4.4 压测时顺便看 CPU（人话诊断）

```bash
top
top -H -p <服务器pid>   # 看是不是某一个线程 100%
```

| 你看到的 | 可能意味着 |
|----------|------------|
| 整体 CPU 很高，QPS 上不去 | 计算忙：memcpy / malloc / Parser |
| CPU 很低，QPS 也低 | 在等：锁、阻塞、设计问题 |
| **一个核 100%，其它核很闲** | 典型单 Reactor / 单 EventLoop 瓶颈 |

粗定位还可：

```bash
perf top -p <pid>
```

看 `malloc`、`memcpy`、`HttpParser`、`mutex` 谁占比高。

## 5. Benchmark-2：对比实验（真正的性能工程）

核心思想：

> 不要「我感觉改这里会快」。  
> 要：**只改一个变量，其它全锁死，测前后差。**

### 实验 A：线程池大小 N = 1 / 4 / 8 / 16

可能出现：

```text
1 → 10000 QPS
4 → 35000
8 → 37000
16 → 36000   ← 线程太多，切换成本吃掉收益
```

结论：存在最优点，不是越大越好。

### 实验 B：Reactor 模型对比（紧贴你的第三阶段）

| 模型 | 结构 | 常见现象 |
|------|------|----------|
| 单 Reactor | accept+读写+业务一锅炖 | 单核打满 |
| Reactor + ThreadPool | IO 与业务分离 | 业务不再堵死 epoll（理想情况） |
| Main + SubReactor | 连接分片到多 EventLoop | 多核吃满、锁减少 |

把结果做成表写进报告——这是简历里很硬的「有数据的架构对比」。

### 实验 C：Keep-Alive 开 vs 关

短连接每次：`connect → 请求 → 响应 → close`（握手成本高）。  
长连接：一条 TCP 打很多请求。  
通常 Keep-Alive **明显抬 QPS**。可用 header `Connection: close` 做对比。

### 实验 D：小文件 vs 大文件

- 小文件：瓶颈常在协议/调度  
- 大文件：瓶颈常在 sendfile / 拷贝 / 磁盘  

### 实验 E：优化案例怎么写才像工程

```text
初始：QPS 20000，P99 20ms
perf：malloc 35%
原因：每请求大量 new string
优化：对象池 / reserve
之后：QPS 32000，P99 8ms
```

这叫优化；「换了个结构体感觉快点」不叫。

## 7. 本章小结

1. 先基线，后优化；用数字说话。  
2. 同时看 **QPS + P99 + Error**，别只追吞吐。  
3. 压测是**发现入口**；解释瓶颈要靠 CPU/perf/Metrics/火焰图。  
4. 一次只改一个变量做对比实验。
