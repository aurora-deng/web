# 00 · 总览与测试分层（详细讲义）

> **这一章先建立「整张地图」**。后面每一章都是地图上的一层。  
> 第三阶段你已经有：Reactor / SubReactor、epoll、非阻塞 Socket、HTTP Parser、Buffer、Router、Executor、Timer、Keep-Alive、Connection 管理。  
> **第四阶段不是再堆协议**（WebSocket / HTTP2 / gRPC 先别上），而是把服务器从「能跑」做成「工程级可验证、可优化、可维护」。

---

## 我对这一层的理解（笔记）

这一阶段不是再写功能，而是给第三阶段服务器补上**工程级验证体系**：

> 从「client → TCP → WebServer → response」升级成：外面有 Benchmark / 故障注入，里面有 Metrics，旁边有 Sanitizer / Fuzz / 火焰图。

分层口诀（自己的话）：

| 层 | 我的理解 |
|----|----------|
| 单元测试 | 预先定义行为，自动验证是否符合预期（测零件） |
| 调试 | 行为不符合时，人进去找原因 |
| 黑盒 | 当客户端真访问，不看内部，只看对不对（测整机） |
| Benchmark | 大量压力下快不快、稳不稳（测性能） |
| Sanitizer | 抓内存/线程类隐藏 Bug |
| 故障注入 | 主动把环境弄坏，看还能不能活 |
| Fuzz | 自动怪输入，看炸不炸 |
| Metrics | 服务器自己记账，告诉我现在忙不忙 |
| 火焰图 | 告诉我 CPU 时间花在哪个函数 |

完整汇总另见：[我对各层测试的理解.md](我对各层测试的理解.md)。

## 1. 这一阶段到底在干什么？

以前你眼里的系统大概是：

```text
client
  │
 TCP
  │
WebServer
  │
response
```

工程级后端眼里的系统是：

```text
              Benchmark（压多少、多快）
                 │
Client -------- WebServer -------- Metrics（里面忙不忙）
                 │
          Fault Injection（坏环境稳不稳）
                 │
       ASan / TSan / UBSan（内存/线程安不安全）
                 │
         FlameGraph / Fuzz（CPU 在哪 / 怪输入炸不炸）
```

一句话：

> **Performance + Reliability Engineering**  
> 性能工程 + 可靠性工程。

简历上也会从「写了个 HTTP 服务器」升级成「有完整验证体系的高性能服务」。

## 2. 为什么要分层？用「造车」类比

把 WebServer 想成一辆车：

| 测试层 | 类比 | 回答的问题 |
|--------|------|------------|
| 单元测试 | 测发动机零件、刹车片尺寸 | 零件本身对不对？ |
| 黑盒测试 | 上路开一圈：灯亮不亮、能不能起步 | 整车行为对不对？ |
| Sanitizer | 拆开看有没有螺丝松、线缠在一起 | 有没有隐藏结构缺陷？ |
| Benchmark | 测极速、百公里加速 | 能跑多快、能扛多久？ |
| 故障注入 | 下雨、爆胎、油不够 | 异常环境还能不能活？ |
| Metrics | 仪表盘：转速、水温、油量 | 现在状态怎样？ |
| 火焰图 | 示波器找哪一段耗电 | 慢在哪个零件？ |
| Fuzz | 乱拧旋钮、乱插接口 | 乱操作会不会直接炸？ |

**只测零件**：车可能装不上。  
**只上路开两下**：发动机内部裂纹测不出来。  
**只测极速**：方向盘失灵时你不知道。  

所以必须**分层**，而且有顺序。

## 3. 推荐学习 / 执行顺序（必须记住）

```text
Phase 1  单元测试 GoogleTest     → 零件对不对
   ↓
Phase 2  HTTP 黑盒 Python TCP    → 用户看到的行为对不对
   ↓
Phase 3  Sanitizer               → 内存/并发隐患
   ↓
Phase 4  Benchmark               → 能扛多少压力
   ↓
Phase 5  故障注入                 → 坏环境下稳不稳
   ↓
Phase 6  Metrics                 → 运行时看得见状态
   ↓
Phase 7  Perf + 火焰图           → 定位 CPU 热点
   ↓
Phase 8  Fuzz                    → 怪输入健壮性（也可与 Sanitizer 并行，主攻 Parser）
```

### 为什么必须「先测再压」？

错误顺序：

```text
直接 wrk -c10000
   → 错误率 20%
   → 不知道是 Parser？Connection？fd？Buffer？
   → 一团乱
```

正确顺序：

```text
单元证明零件 OK
  → 黑盒证明整机行为 OK
  → 再压测看性能
  → 出问题用 Sanitizer / Metrics / 火焰图定位
```

## 4. 每层用一句话说清「它是干什么的」

### 4.1 单元测试（GoogleTest）

**干什么**：测服务器**内部组件**。  
**怎么想**：给函数一个输入，断言输出必须是某个值。  
**不干什么**：不启动完整 accept/epoll 整条链路（或只测局部）。

```text
输入字符串 → Parser → HttpRequest
EXPECT method==GET, path==/hello
```

### 4.2 黑盒测试（Python TCP）

**干什么**：假装自己是浏览器/客户端，真连端口、真发 HTTP。  
**怎么想**：不管里面有没有 epoll，只看「我发了啥、收到啥」。  
**不干什么**：不代替压测（Python 造不出工业级流量）。

### 4.3 Sanitizer（ASan / UBSan / TSan）

**干什么**：编译时给程序「装监控」，跑起来一旦越界、UAF、数据竞争就立刻报。  
**怎么想**：普通运行可能「偶尔正常偶尔崩」；Sanitizer 把偶发变成明确报错。  
**注意**：ASan 和 TSan 一般**不能同时开**。

### 4.4 Benchmark（wrk）

**干什么**：海量请求，测 QPS、延迟、错误率。  
**怎么想**：先建**基线**，再优化，用数字对比，不靠感觉。

### 4.5 故障注入

**干什么**：主动制造延迟、丢包、慢客户端、CPU 打满。  
**怎么想**：生产不是实验室；慢客户端可能耗尽 fd（Slowloris）。

### 4.6 Metrics

**干什么**：服务器自己记账：请求数、连接数、队列长度、延迟分位。  
**怎么想**：不是另开线程「偷看」，而是业务路径上**埋点**，再通过 `/metrics` 读出。

### 4.7 火焰图

**干什么**：告诉你 CPU 时间堆在哪个函数。  
**怎么想**：知道「慢」不够，要知道「慢在 memcpy 还是 Parser」。

### 4.8 Fuzz

**干什么**：机器自动生成乱七八糟的输入砸 Parser。  
**怎么想**：黑盒测「正常/你设计的异常」；Fuzz 测「你想不到的输入空间」。

## 5. 单元测试 vs 断点调试（务必分清）

很多人觉得：「单元测试不就是预判输出再看对不对吗？和打断点差不多。」

**有共同点，但目的不同。**

共同点：

```text
给程序输入 → 观察输出 → 判断是否正确
```

### 调试解决的是：「为什么错？」

测试失败：

```text
Expected: /index.html
Actual:   /index.htm
```

你不知道原因 → 断点进 `parseRequestLine` → 看 `path_start` / `path_end` → 发现写错 → 修好。

### 单元测试解决的是：「以后还会不会再错？」

修好之后留下 `EXPECT_EQ`。一个月后你为了性能把 `string` 改成 `string_view`，指向临时 buffer → 悬空。  
一跑测试立刻 **FAILED**。这叫**回归测试（Regression Test）**。

| | 单元测试 | 断点调试 |
|--|----------|----------|
| 核心问题 | 以后还会不会错？（回归） | 这次为什么错？（定位） |
| 谁判断 | 机器自动 `EXPECT` | 你用人眼看变量 |
| 类比 | 自动化质检流水线 | 老师傅拿放大镜查故障 |

从「打印」到「断言」：

```text
以前：cout << req.path;     → 人眼看是不是 /index.html
现在：EXPECT_EQ(req.path, "/index.html"); → 机器判
```

可以粗暴理解：

> **单元测试 ≈ 自动化的、可重复的「预判输出检查」**；  
> **调试 ≈ 人钻进去找原因**。

## 6. 高性能服务器不能只看「输出对不对」

功能上：

```text
1000 请求 → 1000 成功
```

但可能：

```text
QPS 只有 500（目标 50000）
```

单元测试发现不了「慢」。所以完整闭环是：

```text
正确性 ── GoogleTest / 黑盒
健壮性 ── Sanitizer + Fuzz
性能   ── Benchmark + Perf
观测   ── Metrics
```

## 7. 对本项目，单元测试优先级（笔记）

Bug 和瓶颈大概率扎堆在这些地方：

| 模块 | 优先级 | 为什么 |
|------|--------|--------|
| HttpParser | ★★★★★ | 网络输入、状态机、半包、恶意输入 |
| Buffer | ★★★★★ | 扩容、拷贝、生命周期、string_view 悬空 |
| Reactor / EventLoop | ★★★★★ | fd、回调、跨线程、生命周期 |
| ThreadPool / Executor | ★★★★☆ | 任务排队、唤醒、阻塞是否污染 IO 线程 |
| Timer | ★★★★☆ | 超时回调打到已关闭连接 |
| Router | ★★★☆☆ | 逻辑清晰，但仍要测 404 / 中间件短路 |

纯逻辑（Buffer/Parser/Router）测完后，应进入 **EventLoop / Connection 生命周期**（见第 02 章）——那是分水岭。
