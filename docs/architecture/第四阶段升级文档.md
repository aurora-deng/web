# 第四阶段升级文档

本文是第四阶段 WebSocket 介入与出站任务体系改造的中文教学说明，用"大酒店"生活化比喻讲解每个模块的职责、关键设计与典型流程，适合刚接手项目的中文母语同学阅读。

## 一、本阶段做了什么

### 1.1 总览

第三阶段完成后，服务器已经是一个完整的 HTTP/1.1 服务器：Reactor 驱动 epoll、协程管理读写挂起、Executor 分离业务计算。但 HTTP 是"短轮次"协议——客人问一句，答一句，答完就走——没法支撑 WebSocket 这种"长住、双向聊天"的协议。

第四阶段做的事可以概括成三件：

1. **让服务器能同时接待两种客人**：短住的 HTTP 客人和长住的 WebSocket 客人。抽出一个统一的"住客"基类 `Session`，HTTP 客人和 WS 客人各自实现自己的对话循环。
2. **建一套 WebSocket 协议栈**：握手、拆帧、组帧、分片重组、心跳，全套自研，零外部依赖（连握手用的 SHA-1 都是内置实现）。
3. **重做出站发送体系**：旧版有个叫"HTTP 发送器"的"快递员"专门送 HTTP 响应；新版把它换成一套统一的"出站任务体系"（`OutboundTask` + `OutboundQueue` + `TransportWriter` + `writerLoop` 协程），HTTP 响应和 WS 帧都走这一套，还能跨楼层（跨 Reactor 线程）递送——这是实现"用户 A 给用户 B 发私聊"的关键。

### 1.2 与第三阶段的关系

| 方面 | 第三阶段 | 第四阶段 |
|------|----------|----------|
| 服务对象 | 只有 HTTP 客人 | HTTP 客人 + WS 客人 |
| 协议基类 | 无（HttpSession 直接写） | `Session` 基类，HTTP/WS 并列扩展 |
| 编解码位置 | SubReactor 持有共享的 `HttpCodec` | 下沉到每个 Session 内部，各客人自带翻译官 |
| 发送机制 | 旧版 HTTP 发送器（HTTP 专用） | `OutboundTask` + `OutboundQueue` + `TransportWriter` + `writerLoop`（统一出站） |
| 跨线程推送 | 无 | `postOutbound` + eventfd 唤醒，支持跨 Reactor 投递 |
| 业务分发 | 只有 HTTP 路由 | HTTP 路由 + `WebSocketDispatcher` 按 type 分发 + `WebSocketSessionManager` 全局寻呼 |

核心原则：**不推倒 Reactor，换会话语义与帧模型**。底层的事件循环、协程调度、时间轮都不动，只是把"会话"抽象出来，让 HTTP 和 WS 各自实现自己的对话循环。

## 三、新增模块逐一讲解

> 每个模块按"职责比喻 → 关键代码 → 为什么这样设计"三段式讲解。

### 3.1 协议边界：Session 基类（唯一的抽象基类）

**职责比喻**：`Session` 是所有"住客"的共同身份。不管你是短住的 HTTP 客人还是长住的 WS 客人，在楼层经理眼里都是"一个住客"——会自己跟客人对话（`run()`），以及超时/关闭时的收尾钩子（`onTimeout()`/`onClose()`）。客房（Connection）里挂着一个 `shared_ptr<Session>` 指针，指向当前住客；换住客时只要换这个指针，客房不动。

**关键代码**：[Session.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/session/Session/Session.h)

```cpp
class Session {
  public:
    virtual ~Session() = default;
    virtual Task<void> run() = 0;       // 住客的对话循环（纯虚，子类必须实现）
    virtual bool onTimeout() { return true; } // 超时钩子（默认同意关闭）
    virtual void onClose() {}           // 关闭前清理钩子（默认空）
};
// Connection 里：std::shared_ptr<Session> session;
```

**为什么这样设计**：HTTP 是"读满请求→执行→写完响应"的短轮次，WS 是"长期占用、双向帧流"。如果把两种循环硬塞进一个类，Keep-Alive 状态机和超时语义会打架。抽成基类后，`HttpSession` 和 `WebSocketSession` 各自管自己的对话循环，互不干扰；楼层经理通过基类指针统一唤醒，不用 if 判断协议类型。

> ⚠️ **重要澄清**：旧版文档曾提到 `ProtocolCodec`、`Sender` 两个基类，经源码核实**都不存在**。`HttpCodec` 和 `WebSocketCodec` 都没有继承任何基类（类声明里没有 `: public`）。唯一的协议抽象基类就是 `Session`。

### 3.2 WebSocket 协议层五件套

这一层是"WS 客人自带的翻译官和拆解员团队"，按 RFC 6455 标准实现。

#### 3.2.1 WebSocketTypes / UserId（工具箱）

**职责比喻**：定义 WS 协议里用到的"基本术语"——帧类型（Text/Binary/Ping/Pong/Close）、解码结果（Ok/NeedMore/Error/Closed）、关闭码、用户 ID 类型。

**关键代码**：[WebSocketTypes.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketTypes/WebSocketTypes.h) + [UserId.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketTypes/UserId.h)（`using UserId = uint64_t;`）

#### 3.2.2 WebSocketHandshake（握手接待员）

**职责比喻**：新客人来了先握手。握手接待员检查客人带的"升级申请"（Upgrade 头），算一个"暗号"（Accept Key = Base64(SHA1(Key + GUID))），算对了就回一个"101 同意升级"。

**关键代码**：[WebSocketHandshake.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketHandshake/WebSocketHandshake.h) / [.cpp](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketHandshake/WebSocketHandshake.cpp)

```cpp
bool isUpgradeRequest(const HttpRequest&);   // 是否带 Upgrade: websocket
bool validate(const HttpRequest&);            // GET / HTTP/1.1 + Version=13
void fillResponse(HttpResponse&, 101);         // 填 101 响应 + Sec-WebSocket-Accept
std::string computeAcceptKey(const std::string& key);  // 内置 SHA-1 + Base64
```

**为什么内置 SHA-1**：整个项目只在握手时用一次 SHA-1，为这一次引入 OpenSSL（链接依赖 + 部署复杂度）不划算。内置约 180 行实现，已用 RFC 6455 官方示例验证过。以后上 WSS(TLS) 时再统一换加密库。

#### 3.2.3 WebSocketParser（拆解员团队）

**职责比喻**：客人发的字节流像一封封连续的信，拆解员按"帧"的结构一步步拆：先拆 2 字节头（看 FIN/opcode/长度），再拆扩展长度（126/127 时），再收 4 字节掩码密钥，最后取出 payload 并解掩码。拆一帧走五个阶段，状态机驱动。

**关键代码**：[WebSocketParser.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketParser/WebSocketParser.h) / [.cpp](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketParser/WebSocketParser.cpp)

```text
状态机：BASE_HEADER → EXT_LENGTH → MASK_KEY → PAYLOAD → COMPLETE
组合 4 个子拆解员（都是栈上成员，无动态分配）：
  FrameHeaderParser      拆 2 字节头
  ExtendedLengthParser   展开 126/127 扩展长度
  MaskKeyParser          收 4 字节 mask key
  PayloadParser          取 payload + 解掩码
工具：ParserUtils.h（kWsMaxPayloadBytes=1MB / applyWsMask / isWsControlOpcode）
```

**为什么用状态机+子拆解员**：TCP 是流式字节，一帧可能分多次到达（半包）。状态机能"拆到哪算哪，下次接着拆"，每个子拆解员只管自己那一段，职责单一好测试。

#### 3.2.4 WebSocketCodec（翻译官）

**职责比喻**：翻译官是"业务和协议之间的中间人"。客人发来帧，它拆成业务能懂的消息；业务要发消息，它组帧发出去。它还负责把帧转成"业务信封"（WebSocketMessage），并按 type 把信封交给话务员（Dispatcher）转接。

**关键代码**：[WebSocketCodec.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketCodec/WebSocketCodec.h) / [.cpp](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketCodec/WebSocketCodec.cpp)

```cpp
class WebSocketCodec {  // 注意：无继承
  public:
    WebSocketCodec(WebSocketDispatcher& dispatcher);
    WsDecodeResult decode(Buffer&, WsFrame&);           // 委托 Parser 拆帧
    WebSocketMessage messageFromFrame(const WsFrame&);   // 帧→业务信封（支持 JSON / @user:text / echo）
    void dispatch(WsMessageContext&);                    // 委托 Dispatcher 转接
    static std::string encodeText(const std::string&);   // 组 Text 帧（服务端不掩码）
    static std::string encodeBinary(...);
    static std::string encodeClose(code, reason);
    static std::string encodePing/encodePong(...);
};
```

**为什么服务端发帧不掩码**：RFC 6455 §5.1 规定服务端发给客户端的帧不必掩码。掩码是为了防止中间代理缓存中毒，服务端是数据源，不需要掩码。这省了一道编解码开销。

### 3.3 WebSocket 会话层：WebSocketSession（长住客人）

**职责比喻**：长住客人的对话循环——先到登记台登记入住（registerSession），然后一直循环收帧、处理帧（Close 就回写关闭、Ping 就回 Pong、分片就攒起来、Text/Binary 就交给话务员转业务）。自带翻译官（codec_）和拆解员（parser_）。

**关键代码**：[WebSocketSession.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketSession/WebSocketSession.h) / [.cpp](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketSession/WebSocketSession.cpp)

```cpp
class WebSocketSession : public Session, public enable_shared_from_this<WebSocketSession> {
    // 成员：reactor_ / fd_ / uid_ / manager_ / parser_ / codec_ / state_ / fragmentBuf_ / fragmentOpcode_
    Task<void> run();  // registerSession → 帧循环 → handleAppMessage
    void handleAppMessage(const WsFrame&);   // 组 WsMessageContext → codec_.dispatch → 有 outbound 就 enqueueOutbound
    void enqueueOutbound(std::string bytes, OutboundCompletion);  // 调 reactor_->enqueueOutbound
};
```

**为什么继承 enable_shared_from_this**：登记入住时要把自己（shared_ptr）交给登记台存 weak_ptr，必须用 `shared_from_this()` 拿到安全的 shared_ptr，不能用 `this`（会悬空）。

### 3.4 WebSocket 业务层三件套（旧文档完全没讲）

> 这是第四阶段的"业务大脑"，决定"消息往哪转、怎么跨楼层递送"。旧版文档完全没提，是理解点对点聊天的关键。

#### 3.4.1 WebSocketMessage / WsMessageContext（业务信封 + 工作单）

**职责比喻**：
- `WebSocketMessage` 是**业务信封**：装着消息类型（type）、文本、帧类型、收件人、发件人。比"裸帧"更贴近业务。
- `WsMessageContext` 是**工作单**：一次业务处理需要的全部信息——进来的信封（inbound）、要发出去的信封（outbound）、是否要回发、当前用户、住客指针、登记台指针。话务员（Dispatcher）拿着工作单转接业务。

**关键代码**：[WebSocketMessage.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketMessage/WebSocketMessage.h) + [WsMessageContext.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketDispatcher/WsMessageContext.h)

```cpp
struct WebSocketMessage {
    std::string type;          // "chat" / "broadcast" / 自定义
    std::string text;          // 文本内容
    WsOpcode opcode;           // Text / Binary
    UserId toUserId;            // 收件人
    UserId fromUserId;          // 发件人
};
struct WsMessageContext {
    WebSocketMessage inbound;   // 进来的消息
    WebSocketMessage outbound;  // 要发出的消息
    bool hasOutbound;            // 是否需要回发
    bool keepConnection;         // 处理完是否保持连接
    UserId uid;                  // 当前用户
    WebSocketSession* session;
    WebSocketSessionManager* manager;  // 拿到登记台，才能跨楼层递送
};
```

**为什么不直接用帧**：帧是"协议层"概念（FIN/opcode/mask），业务不关心这些。业务信封抽掉协议细节，只留 type/text/收发人，业务代码写起来清爽。

#### 3.4.2 WebSocketDispatcher（话务员）

**职责比喻**：话务员负责"按 type 转接业务"。业务方提前告诉话务员"遇到 type=chat 的信封，交给这个 handler 处理"。来了一份工作单，话务员先按 type 精确匹配找 handler；找不到就走默认 handler（echo 回显）。

**关键代码**：[WebSocketDispatcher.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketDispatcher/WebSocketDispatcher.h) / [.cpp](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketDispatcher/WebSocketDispatcher.cpp)

```cpp
using WsHandler = std::function<bool(WsMessageContext&)>;
void on(const std::string& type, WsHandler handler);   // 注册：type="chat" → 私聊 handler
void onDefault(WsHandler handler);                      // 注册默认：echo
void dispatch(WsMessageContext& ctx);                     // 先精确匹配，再 fallback default
```

**为什么不写在 Session 里**：业务分发逻辑和协议循环解耦。换业务只要换 handler 注册，不用动 WebSocketSession。main.cpp 里 `server.wsDispatcher().on("chat", ...)` 就能加新业务。

#### 3.4.3 WebSocketSessionManager（登记台 / 住客寻呼簿）

**职责比喻**：大酒店前台的"住客登记簿"。每个 WS 客人入住时记下"我是 uid=1001，住在 reactorIndex=2 这条线程的 fd=55 房间"。有人想给 uid=1001 送消息，先翻登记簿找到他在哪条线程哪个房间，然后叫那条线程的客房服务员送去——自己不冲上楼。

**关键代码**：[WebSocketSessionManager.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketSessionManager/WebSocketSessionManager.h) / [.cpp](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/websocket/WebSocketSessionManager/WebSocketSessionManager.cpp)

```cpp
struct Locator {
    std::weak_ptr<WebSocketSession> session;  // 弱引用：住客退房自动失效，不卡住房间不让拆
    size_t reactorIndex = 0;                   // 楼层号（哪条线程）
    int fd = -1;                              // 房间号
    uint64_t connId = 0;                      // 防错编号（fd 复用时认对人）
};
std::unordered_map<UserId, Locator> sessions_;  // 登记簿主体

bool registerSession(uid, session, reactorIndex, fd, connId);  // 入住登记
EnqueueResult sendEncoded(uid, encodedBytes);                   // 查表→跨楼层递送并返回准入结果
EnqueueResult sendText(uid, text);                              // = encodeText + sendEncoded
size_t broadcastText(users, text);                             // 广播（共享同一帧）
```

**为什么用 weak_ptr**：住客的真实归属在客房（Connection::session 是 shared_ptr）。登记簿若也持 shared_ptr，住客退房时客房想拆房间，可登记簿还指着它，房间拆不掉——这就是循环引用导致的内存泄漏。weak_ptr 只"观察"不"拥有"，住客退房时 weak_ptr 自动失效，登记簿检测到失效就顺手擦掉那条死记录（惰性清理）。

**为什么单独记 reactorIndex/fd/connId**：weak_ptr 只能告诉你"还活着"，不能告诉你"在哪条线程"。跨楼层递送必须知道楼层号（reactorIndex）才能调 `postOutbound`；fd/connId 用于在目标楼层精确找到那间客房（connId 防 fd 复用认错人）。

### 3.5 出站任务体系（OutboundTask + OutboundQueue + writerLoop + postOutbound）（旧文档完全没讲）

> 旧版有个 HTTP 发送器类（"快递员"）专门送 HTTP 响应。新版**没有 Sender 类了**，换成一套统一的"出站任务体系"。HTTP 响应和 WS 帧都走这一套。这是第四阶段最容易被旧文档误导的地方。

#### 3.5.1 OutboundTask（发件任务）

**职责比喻**：所有要发出去的东西都打包成"发件任务"。任务里装着三种货之一：已编码的 WS 帧（encoded）、HTTP 响应（http，含 sendfile）、广播共享帧（sharedEncoded，多个收件人共享同一份字节避免重复拷贝）。任务还带一个"顺序票据"（ticket）保证 HTTP 响应按请求顺序发出。

**关键代码**：[OutboundTask.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/transport/OutboundTask.h)

```cpp
class OutboundTask {
    using Payload = std::variant<EncodedBufferTask, SharedEncodedBufferTask, HttpStreamTask>;
    static OutboundTask encoded(std::string bytes, ticket=0, completion=None);
    static OutboundTask http(PooledHttpResponse, ticket, completion=None);
    static OutboundTask sharedEncoded(std::shared_ptr<const std::string>, ticket=0, ...);
    Payload payload; uint64_t ticket; OutboundCompletion completion;
};
```

**为什么用 variant 统一**：WS 帧、HTTP 响应、广播三种出站需求共用一套冲刷逻辑（writev 聚集、背压），避免协议分叉。旧版 Sender 是 HTTP 专用，加 WS 就得再写一个 WSSender，重复造轮子。

#### 3.5.2 TransportWriter（打包发货窗口）

**职责比喻**：发货窗口把任务队列里的货打包发出。已编码的字节用 `writev` 一次性聚集发出（少调几次系统调用）；HTTP 大文件用 `sendfile` 零拷贝。积压太多（超 4MB）就暂停收货（撤销读关注），降到 2MB 再恢复——这就是背压。

**关键代码**：[TransportWriter.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/transport/TransportWriter.h) / [.cpp](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/transport/TransportWriter.cpp)

| 常量 | 值 | 作用 |
|------|----|------|
| kWriteHighWatermark | 4MB | 积压超此触发背压，暂停读 |
| kWriteLowWatermark | 2MB | 积压降到此恢复读 |
| kMaxOutboundTasks | 4096 | 单连接任务上限防 OOM |

#### 3.5.3 writerLoop 协程（专职发件员）

**职责比喻**：每间客房配一个专职发件员（writerLoop 协程）。有人下单（enqueueOutbound）就唤醒他去发货（flush）；货发完就歇着等下一单。一间客房只有一个发件员，保证发出的字节不会交错（多个发件员并发写会破坏帧边界）。

**关键代码**：[SubReactor.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/SubReactor/SubReactor.h) 里 `Task<void> writerLoop(int fd, uint64_t connId)`

```text
processPendingFds 建客房时，同时启动 writerLoop 协程 + scheduler.adopt
writerLoop 循环：
  co_await 等待 OUTBOUND 唤醒 → transportWriter.flush → 发完继续等
  EAGAIN → updateEvent(EPOLLOUT) + co_await 等可写
  出错 → fd_close
```

#### 3.5.4 postOutbound（跨楼层递送）

**职责比喻**：跨楼层送东西不能自己冲上别人的楼层（那是别人线程的地盘，会打架）。正确做法：把货放到目标楼层的"暂存货架"（OutboundQueue 的 pending 队列），按门铃（write eventfd）叫醒目标楼层的经理，让他自己人去取货上架。

**关键代码**：[ReactorGroup.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/Reactor/ReactorGroup.h) 的 `postOutbound` + [SubReactor.h](file:///e:/虚拟机高级web开发/web-test/web-test6.1/server/SubReactor/SubReactor.h) 的 `postOutbound/processPendingOutbound`

**为什么不能直接跨线程操作**：客房表（conns）只允许本楼层经理自己访问（无锁设计）。跨线程直接碰目标楼层的客房，会跟目标线程的 epoll/协程逻辑竞争。eventfd 把任务暂存队列，唤醒目标线程自己处理，所有客房操作集中在本线程，消除数据竞争。

## 五、典型业务流程串讲

### 5.1 HTTP → WebSocket 升级握手

```text
1. 客人发来 GET /ws?uid=1001 + Upgrade 头
2. HttpSession::run 收请求 → HttpCodec::decode → 扔给 Executor 执行路由
3. 路由 handler 调 ctx.acceptWebSocket() → webSocketAccepted=true
4. HttpSession 检查标志 → 是升级 → prepareWebSocketUpgrade()
5. WebSocketHandshake::validate 校验 → fillResponse(101) + Accept Key
6. 发 101：reserveOutboundTicket → OutboundTask::http → enqueueOutbound → 等发完
7. 101 发送成功 → handoffWebSocket()
8. 从 URL 取 uid → 配置心跳 → 创建 WebSocketSession
9. conn->session = ws（换住客）→ scheduler.adopt(WS 协程)
10. HttpSession 协程结束（co_return），WS 协程被 runReady 启动
```

### 5.2 WebSocket 帧循环

```text
WebSocketSession::run 启动：
  registerSession(uid, self, reactorIndex, fd, connId)  ← 到登记台登记入住
  while (state == Open):
    codec_.decode(readBuffer, frame)       ← 拆帧
    NeedMore → 继续读 → 仍 NeedMore 就 co_await ReadAwaiter 等 EPOLLIN
    Close → 回写 Close → fd_close → 结束
    Ping → enqueueOutbound(encodePong)    ← 自动回 Pong
    Pong → touchActivity → continue        ← 刷新活动时间
    Continuation → 攒到 fragmentBuf_（FIN=1 时重组）
    Text/Binary → handleAppMessage:
      messageFromFrame（帧→业务信封）
      组 WsMessageContext 工作单
      codec_.dispatch(ctx)  ← 交给话务员
        命中 type handler → 执行业务
        未命中 → defaultHandler（echo 回显）
      ctx.hasOutbound → enqueueOutbound(OutboundTask::encoded)
```

### 5.3 点对点聊天：A 在 Reactor0 给 B 在 Reactor2 发消息

```text
① A 连上 ws://host/ws?uid=1001（被分到 Reactor0）
   B 连上 ws://host/ws?uid=1002（被分到 Reactor2）

② A 发送 Text 帧：{"type":"chat","to":1002,"content":"hello"}

③ Reactor0 的 WebSocketSession[0] 收到帧 → handleAppMessage
   → codec_.dispatch(ctx) → 命中 "chat" handler
   → handler 调 ctx.manager->sendText(1002, "hello")

④ 登记台 sendText：
   → WebSocketCodec::encodeText("hello") 编码成 WS 帧（在 A 的线程做）
   → sendEncoded(1002, bytes)
   → 锁内查 sessions_[1002] → 拷贝 Locator{reactorIndex=2, fd, connId}
   → 检查 weak_ptr 未 expired（B 还在线）
   → 锁外调 reactorGroup_->postOutbound(2, fd, connId, OutboundTask::encoded(bytes))

⑤ ReactorGroup::postOutbound → reactors_[2]->postOutbound(...)
   → Reactor2 不是当前线程 → 锁 push pendingOutbound_ → write(eventfd) 按门铃

⑥ Reactor2 楼层经理 loop 醒来（eventfd 响）→ processPendingOutbound
   → 锁内 swap 出暂存队列 → 逐条按 fd+connId 校验 B 的客房还在
   → enqueueOutbound → transportWriter.enqueue（挂到 B 的出站队列）
   → wakeCoroutine(fd, Writer, OUTBOUND)  ← 唤醒 B 的发件员

⑦ B 的 writerLoop 发件员被唤醒 → transportWriter.flush → writev 发出

⑧ B 的浏览器收到 Text 帧 "hello" ✅
```

**关键纪律**：整个过程 A 不知道 B 在哪条线程，登记台也不知道——它只管查表。真正跨线程的递送由 eventfd 转交，B 所在的 Reactor2 自己线程处理，绝不跨线程碰客房表。

## 六、设计取舍说明

1. **为何用 OutboundTask 取代旧版 HTTP 发送器**：旧版 Sender 是 HTTP 专用的同步发送器。引入 WS 后出站需求变多（WS 帧、HTTP 响应、广播），还需要 writev 聚集和 sendfile 零拷贝。OutboundTask 用 variant 统一三种货，TransportWriter 统一冲刷，writerLoop 串行化——一套体系服务 HTTP 和 WS，避免协议分叉。

2. **为何 SessionManager 用 weak_ptr 而非 shared_ptr**：住客真实归属在客房（Connection::session 是 shared_ptr）。登记台若也持 shared_ptr，住客退房时客房想拆房间可登记台还指着，房间拆不掉（循环引用泄漏）。weak_ptr 只观察不拥有，住客退房自动失效，登记台检测到就擦掉死记录。

3. **为何每连接单 writerLoop 协程**：把出站 I/O 串行化到一个协程，避免多个发件员并发写导致帧字节交错破坏协议边界。和读协程（Reader）并列但分槽互不干扰，读快写慢时由背压自动节流。单协程也让"顺序票据"（ticket）简单推进。

4. **为何点对点聊天走 SessionManager 而非直接投递**：跨楼层递送必须知道目标在哪条线程。住客只知道自己楼层，不知道别人在哪。登记台维护全局"UserId → 位置"目录，调用方只需 `sendText(uid, text)`，登记台查表后递送，屏蔽"目标在哪条线程"的细节。

5. **为何跨 Reactor 用 eventfd 而非直接加锁**：客房表（conns）只允许本楼层线程访问（无锁设计）。跨线程直接碰目标客房会跟目标线程的 epoll/协程竞争。eventfd 把货暂存队列，唤醒目标线程自己处理，所有客房操作集中在本线程，消除数据竞争。

6. **为何会话交接而非在 HttpSession 里硬塞帧循环**：HTTP 是短轮次，WS 是长连接双向流，硬套会破坏 Keep-Alive 状态机和超时语义。交接模型：HttpSession 发完 101 就 co_return 结束，客房换持 WebSocketSession，两种循环完全隔离。

7. **为何握手仍走 Executor**：复用现有路由和中间件（鉴权、日志），升级决策和 HTTP 业务同一套分发；真正的帧 I/O 仍在 Reactor 协程，Worker 不碰客房表，保持线程安全。
