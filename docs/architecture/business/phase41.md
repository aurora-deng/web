## 3. 本机入口的约2秒延迟修复

初版只绑定127.0.0.1，URL为localhost。Windows先尝试IPv6时出现固定延迟；现在127.0.0.1和::1同时监听，同一个Host/Origin策略与连接/流/缓冲上限仍然生效。

| 轮次 | 修复前代理附加P50 | 修复后代理附加P50 |
|---|---:|---:|
| 1 | 1967.595ms | 21.002ms |
| 2 | 1967.068ms | 12.074ms |
| 3 | 1961.936ms | 12.636ms |

每轮各30个新连接请求，比较同一Schannel证书验证路径的直接TLS请求与本机代理请求；实际网络经已授权SSH转发。修复后的代理总P50约190–202ms，直接TLS约178–187ms。这是包含连接/TLS与客户端解析的往返测量，**不是纯Reactor延迟**，也不代表浏览器复用连接后的延迟。当前普通上游HTTP仍为每请求新连接，WS/SSE则保持长连接。

Release本机空闲工作集12.281MiB、观察峰值16.148MiB；Debug完整AI链路空闲12.273MiB、峰值16.352MiB。范围为原生本机进程，不含浏览器、按需解析进程或Linux模型Worker；满足空闲200MiB目标。

## 4. 独立模型Worker的真实结果

复用已经安装、已校验的 `phi3-mini-4k-instruct-cpu-int4`，测试夹具新建独立的grpc运行方式绑定，没有修改正式模型版本。配置为1个推理Worker、最多1个驻留模型、排队2个，loopback50062、TLS及私有Token。

| 状态 | 服务端首Token | 本次总耗时 |
|---|---:|---:|
| 进程冷态、模型未驻留 | 25.745s | 29.764s |
| 相同模型已驻留 | 1.225s | 5.457s |
| Worker重启后的首次生成 | 24.876s | 25.885s |

前两次使用同一简短中文问候、最多32输出Token；重启恢复使用更短的8Token请求。这里的冷态没有清空操作系统文件缓存，不是整机冷启动。模型驻留工作集约3223–3226MiB，不外推其他模型、长上下文或多用户并发性能。

强制结束经过PID与启动标识核验的**测试Worker**后，私人任务明确失败，主服务存活，普通好友消息仍能持久化；重启Worker后真实生成恢复。这些私人推理请求没有产生服务器消息记录；同一模型用于群聊时，公共群聊结果仍按正常规则持久化。

Windows Debug完整链路进一步验证：一次正常完成、一次主动取消，引用数量分别1和2，本机历史终态正确。首段返回分别31.953s/25.875s，包含不同的RAG/历史输入、本机轮询和网络，不能与上表短输入纯服务端指标直接比较。

真实群AI另外验证了 `mention` 和 `reply`：SSE分别收到1073/1111字节，完成后群历史中分别有1/2条AI消息。观测首Token约15.558s/30.101s；第二次包含更长群历史，因此不能把“模型已驻留”理解为所有输入都会相同延迟。该测试只证明业务与协议链路，不证明模型严格遵从“一句话”指令或回答质量。

代码：[Worker控制脚本](../../../scripts/function3/validation/onnx_worker.py)、[真实故障测试](../../../tests/function3/integration/worker_isolation_blackbox.py)。模型加载与驻留改善来自实际复用，不归因于目录改名。

## 6. 数据库等待诊断

另外执行只用于定位的同步提交对照，给测试连接启用IO计时，通过已安装libpq每20ms观察等待类别，不采集SQL正文、用户输入或Key。诊断结果与正式三轮分目录保存。

同步提交诊断中，当前版本记录715次客户端WAL同步、累计约2030.947ms；活跃等待主要为 `IO:WalSync` 和 `LWLock:WALWrite`。该轮ACK P99为115.154ms。

仅对独立测试子进程连接设置 `synchronous_commit=off` 的因果对照中，当前版本客户端同步计数为0，ACK P99降至60.246ms。该配置改变持久性，**不用于验收、不用于日常启动，也没有写入PostgreSQL全局配置或应用默认值**。

性能采集后又将启动迁移门禁从021加强到022；这不改变通信/聊天热路径。

这些证据支持数据库/WAL同步与虚拟机IO抖动是重要来源；异步对照仍有约60ms尾延迟，因此不能声称已经定位或修复全部根因。现有360个ACK样本的P99也会受少量尾部样本影响。后续应在稳定IO条件下扩大样本，并进一步分解数据库执行器排队、提交、Reactor恢复与发送耗时；本轮不通过降低可靠性追求门槛。

## 7. 教学：如何沿接口读代码

可以把通信内核看成“收发室”，共享业务看成“办理业务的窗口”，Windows私人助手看成“自己的资料柜”。收发室识别连接与协议，窗口判断权限与事务，资料柜只把获准的必要片段交给模型。

1. **先跟一条普通消息**：`ChatApp` → WS DTO → Transport → ChatService → Repository → 消息/Outbox同事务 → 真实ACK与推送。找出哪一步成功才能称为“服务器已保存”。
2. **再跟一次私人提问**：`AssistantPanel` → LocalAssistantApi → LocalAssistantService → 本机检索/记忆 → PrivateGenerationHttp → PrivateGenerationService → PrivateModelRouter → gRPC Worker → token → 本机历史。解释为什么这条路没有调用服务器ChatService。
3. **再看确认式写入**：草稿 → ActionService保存固定载荷及摘要 → 用户确认id/digest → 本机代理 → 正常业务API再次鉴权/幂等。取消不能被当成确认，模型自由文本也不能直接执行。
4. **最后跟一枚果实**：ActivityPublisher选择频道和可见范围 → 活动/树服务 → PostgreSQL/Outbox → 排名/公告 → 本地投递或MQ → SSE → 3D场景/音频。解释为什么仅个人主页的内容不会增加树大小和全站热度。

每次只沿一条链读，重点标出：输入、身份、线程、事务、幂等键、取消状态、输出上限及错误返回。后续学习可分别对照[Phase37](phase37.md)、[Phase38](phase38.md)、[Phase39](phase39.md)、[Phase40](phase40.md)，不需要一次读完全部组件。
