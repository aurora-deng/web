# Phase48 学习讲义：拆分以后，为什么事务和页面仍能连起来

## 1. 拆分的是岗位，保留的是同一本账

原 PostgresStore 像一个窗口同时办理账号、聊天、模型和训练。现在它只负责把当前任务的数据库连接交给对应专员：

```cpp
auto transaction = database.beginTransaction();
// 下面两个 Port 经门面取得同一个 Worker 绑定的 PGconn。
auto message = messages.appendMessage(input);
outbox.appendOutbox(eventFor(message));
transaction->commit();
```

不能让消息驱动和 Outbox 驱动各自借连接后分别 commit，否则一边成功、一边失败时会留下“已保存但没有通知”或“通知了但没有消息”的半成品。驱动收到的是现有连接，不拥有连接池。

内存测试也不是每个领域新建一个容器仓库。它们引用同一个 MemoryState；事务回滚恢复整份快照，因此可以运行与 PG 相同的跨领域契约。

## 2. 为什么薄门面仍有很多方法

原服务依赖既有 Repository Port，兼容门面暂时实现这些接口，再转交领域实现。门面像总机，只接线；SQL与行映射不再堆在总机里。

判断是否解耦，应该看：业务是否只依赖端口、驱动是否只承担对应领域、事务是否仍统一、组件能否独立验证。不能只把一个源文件改成十份包含相同私有状态的实现片段。

## 3. 前端“共享状态”与“共享全部能力”不同

页面需要共同知道当前账号、会话和取消状态；但消息组件不需要账号管理的全部命令。ChatScope像一张岗位权限卡：

```javascript
const scope = createChatScope(context, {
  resources: ['state', 'elements'],
  commands: ['sendSocket', 'setStatus'],
  types: [],
  events: true,
});
// scope.actions.sendSocket 可用；未声明的管理命令不可见。
```

命令在调用时才找到实际控制器，解决装配先后顺序；资源仍引用同一会话对象。事件监听共用页面生命周期的 AbortSignal，页面销毁后统一撤销。这样既不会复制第二份消息状态，也减少隐式跨模块调用。

## 4. 颜色变量应该表达用途

`--surface`表示卡片或面板，`--text-3`表示次要说明，`--on-accent`表示强调按钮上的文字。深浅主题给这些角色分配不同颜色，组件不再自己决定“这里永远是白字”。

本轮实际发现并修复了这个反例：浅色主题下，一个旧 `--chat-text`覆盖把文字变成接近白色，背景也变白。仅检查按钮能切换主题不会发现它；必须检查页面真实颜色并看截图。

品牌导航另用 `--brand-*`，避免树页面的玫瑰强调色顺带改变全局导航。3D材质色与UI语义色分开维护，保留神树美术表现。

## 5. Outbox 批量确认省在哪里

旧流程是“投递一件 → 写一次已投递标记 → 同步提交”，连续几十件可能连续刷盘几十次。新流程先按顺序投递一个有界前缀，再一次性标记这一批。

```text
事件1成功 → 事件2成功 → 事件3失败 → 不尝试事件4
                    ↓
            一次确认事件1、事件2
```

如果确认前进程退出，事件1、2会重投；这要求消息 ID、事件 ID 和 Inbox 去重保持有效。优化改变的是数据库提交次数，不改变业务 ACK、送达和已读的意义。

## 6. 自检

1. 把消息和 Outbox 放到两个连接提交，会出现哪两种半成品？
2. 为何内存实现拆分后不能各自保存一份独立 State？
3. 为何输入框变白、主题按钮能切换，仍不代表文字一定可读？
4. 第3个事件发布失败时，前2个与第4个分别应如何处理？
5. 批量确认前崩溃时，为何允许重投，却不能换一套事件 ID？

先沿这几个问题读一遍代码，再学习下一轮的任务调度与性能定位；无需立即扩展微服务或更换通信核心。
