# 机器人 C++ 系统软件 9–12 个月路线图

## 阅读定位与规划动机

本文用于回答“从当前 C++ Web 系统软件基础转向机器人后，学什么、为什么按此顺序学、每阶段如何验收”。
路线按 ROS 2 工程骨架、DDS/QoS、实时 Linux、CAN/设备接入、ros2_control 逐层推进，因为后一步都依赖
前一步建立的通信、调度、测量或硬件抽象能力；用阶段项目和量化门禁代替课程清单，是为了控制跨度并让
每段投入都形成可展示、可复现的交付。

当前 HTTP Server 不是与机器人方向无关的旧项目，而是迁移起点：其 Reactor/协程模型训练异步通信和
线程边界，增量解析训练设备协议状态机，测试与 [性能实验](../performance/BENCHMARK.md) 训练故障复现和数据证据，
[架构说明](../architecture/ARCHITECTURE.md) 中的所有权、背压与关闭分析则可用于比较 ROS 2 executor、DDS 队列和
设备生命周期。迁移强调方法复用而非代码硬搬，特别是实时控制路径不能直接沿用动态分配、阻塞 handler
或未经界定的协程调度。

这份规划也给 Web 明确收口：保留现有服务作为 C++/Linux 作品、工程能力证明和未来机器人诊断面板的
轻量入口，只补稳定性、安全、配置与验证缺口，不再扩张前端或服务端框架。这样既保留就业兜底，
又把主要学习时间转向 ROS 2/DDS、实时性和设备接入，减少双主线竞争。

## 目标与边界

这条路线面向 2027 年底考研，同时兼顾本科阶段求职的高薪与稳定性。主方向不是“全栈机器人”，而是机器人/智能汽车中的 **C++ 系统软件与中间件**：先掌握 ROS 2/DDS，再补实时 Linux 与车载/工业总线，最后进入 ros2_control 和必要的控制基础。

完成路线后，应具备以下可展示能力：

- 能解释并定位 ROS 2 节点间通信的发现、QoS、序列化、执行器和线程问题。
- 能在 Linux 上测量并改善通信链路的延迟、抖动、丢包和 CPU 占用。
- 能接入 CAN 或 SocketCAN，设计可靠的设备协议适配层。
- 能实现一个 ros2_control 硬件接口，并完成基础闭环控制。
- 能把项目做成可复现、可测试、有性能数据的工程，而不只是运行教程示例。

建议按 **10 个月主线 + 2 个月机动** 执行。若考研或课程压力增大，可延长到 12 个月，不通过压缩项目验收来“赶进度”。

## 总体投入与每周比例

常态投入建议为每周 12–16 小时，最低有效投入为每周 8 小时。机器人主线内部按以下比例分配：

- 45%：项目编码、调试和集成。
- 25%：原理学习与最小实验。
- 15%：测试、性能测量和故障复现。
- 10%：阅读官方文档、源码关键路径或设计文档。
- 5%：整理 README、架构图、实验记录和复盘。

此外，全部可支配学习时间建议这样分配：

- 非考研冲刺期：机器人系统软件 50%，考研基础 35%，学校课程与 Web 保温 15%。
- 考研强化期：机器人系统软件 25%，考研 65%，学校课程与 Web 保温 10%。
- 考研冲刺期：机器人系统软件 5%–10%，考研 85%–90%，其余只处理硬性任务。

Web 不再单独扩展新框架，只保留工程能力和必要的就业兜底。

## 阶段一：ROS 2 工程基础与通信模型（第 1–2 个月）

### 学习目标

- 从“会使用 ROS”升级到理解 ROS 2 通信和运行时模型。
- 熟悉 package、workspace、launch、参数、日志、接口定义和生命周期节点。
- 理解 topic、service、action 的适用边界，以及 executor、callback group、线程模型。
- 建立可测试、可观测的 C++ ROS 2 工程骨架。

### 具体技术栈

- Ubuntu LTS、ROS 2 的一个 LTS 发行版、colcon、ament_cmake。
- C++17/20、rclcpp、launch、rosbag2、tf2、GoogleTest。
- clang-format、clang-tidy、GDB、AddressSanitizer/UndefinedBehaviorSanitizer。
- CMake、Git；Docker 仅用于固定开发环境，不作为学习重点。

### 项目交付：可观测的多节点数据管线

实现一个模拟智能车传感器数据管线：

1. 传感器节点按可配置频率发布带时间戳的数据。
2. 处理节点使用线程安全队列完成过滤或聚合。
3. 监控节点统计端到端延迟、频率、丢帧和超时。
4. 使用参数和 launch 切换频率、队列深度和执行器配置。
5. 用 rosbag2 录制并回放测试数据。

### 验收标准

- 一条命令可完成构建，一条命令可启动完整系统。
- 至少包含 3 个 C++ 节点、1 个自定义消息和 1 个 service 或 action。
- 能用实验说明单线程/多线程 executor 与 callback group 的行为差异。
- 有不少于 5 个单元或集成测试，异常退出和明显内存错误为零。
- README 给出架构图、运行步骤、测试命令和一组延迟统计结果。

## 阶段二：DDS、QoS 与通信性能（第 3–4 个月）

### 学习目标

- 理解 DDS 的 participant、publisher/subscriber、discovery、domain 和 QoS。
- 能根据传感器流、控制指令、状态同步等场景选择 QoS。
- 理解 ROS 2 到 DDS 的映射、序列化成本与进程内/进程间通信差异。
- 建立“先测量、再优化”的性能排查方式。

### 具体技术栈

- ROS 2 QoS：reliability、durability、history、depth、deadline、lifespan、liveliness。
- 至少对比两种常用 RMW/DDS 实现，不要求深挖全部源码。
- Wireshark、ros2 tracing 或 LTTng、perf、top/htop。
- Linux 网络基础：UDP、组播、socket buffer、丢包与 MTU。

### 项目交付：ROS 2/DDS QoS 基准与故障实验台

扩展阶段一项目，形成可重复运行的 benchmark：

- 对比不同消息大小、发布频率、QoS、RMW 和进程部署方式。
- 注入订阅者延迟、CPU 压力、网络抖动或丢包。
- 输出 P50/P95/P99 延迟、吞吐、丢包率和 CPU 占用。
- 为传感器数据、控制命令、设备状态各给出一套 QoS 选择及理由。

### 验收标准

- benchmark 参数可配置，结果可导出 CSV/JSON；脚本能重复生成统计。
- 至少完成 12 组有效对照实验，每组说明变量、环境和结论。
- 能现场解释“可靠传输不等于低延迟”和队列积压造成的尾延迟。
- 能定位并复现至少 3 类通信故障：QoS 不兼容、发现失败、处理不及时或网络丢包。
- 优化前后有数据对比，不能只写主观结论。

## 阶段三：实时 Linux、并发与时延工程（第 5–6 个月）

### 学习目标

- 理解实时性关注的是最坏情况和抖动，而非平均速度。
- 掌握线程调度、优先级、CPU 亲和性、内存锁定、缺页和优先级反转的基础。
- 能识别动态分配、锁竞争、日志和阻塞 I/O 对实时路径的影响。
- 能设计非实时路径与准实时控制路径之间的边界。

### 具体技术栈

- Linux pthread、SCHED_FIFO/SCHED_RR、CPU affinity、mlockall。
- PREEMPT_RT 的概念、安装和对比测试；不要求自行维护内核。
- cyclictest、perf、ftrace/trace-cmd。
- C++ 并发：atomic、mutex、condition_variable、有界队列、RAII。
- 基础无锁思想；只在测量证明锁是瓶颈时实现无锁结构。

### 项目交付：固定周期执行器与实时性报告

实现一个独立 C++ 周期任务框架，并接入 ROS 2 数据输入：

- 以 1 kHz 或硬件允许的稳定频率运行模拟控制循环。
- ROS 2 回调位于非实时线程，通过有界缓冲区交换数据。
- 对比普通内核与 PREEMPT_RT（若设备支持），以及不同负载和线程配置。
- 记录周期误差、最大延迟、P99.9 延迟、超期次数和 CPU 占用。

### 验收标准

- 连续运行至少 30 分钟，无崩溃、无无界内存增长。
- 在压力负载下能输出抖动直方图和最坏情况数据。
- 能通过代码与架构图指出实时路径，说明其中哪些操作被禁止及原因。
- 至少完成一次锁竞争或调度问题的复现、定位和修复，并保留前后数据。
- 若无法使用 PREEMPT_RT，必须明确设备限制，以普通内核对照实验替代，不伪造实时结论。

## 阶段四：CAN/SocketCAN 与设备接入（第 7–8 个月）

### 学习目标

- 掌握 CAN 帧、仲裁、位速率、错误状态和总线负载的基础。
- 熟悉 SocketCAN 编程、过滤、超时、重连和故障处理。
- 理解设备驱动、协议解析与上层 ROS 2 接口之间的分层。
- 形成面向智能汽车/移动机器人的硬件抽象意识。

### 具体技术栈

- CAN 2.0 基础、SocketCAN、can-utils、vcan。
- Linux socket、poll/epoll、时间戳、字节序、CRC/计数器。
- ROS 2 diagnostics、参数与 lifecycle。
- 可选真实硬件：USB-CAN、带 CAN 的开发板或电机驱动器；没有硬件时使用 vcan 和仿真节点。

### 项目交付：健壮的 CAN 设备网关

实现一个 C++ CAN 网关：

- 原始 SocketCAN 层负责收发、过滤、时间戳和错误处理。
- 协议层负责打包/解包、范围校验、计数器和超时检测。
- ROS 2 层发布设备状态并接收控制命令。
- 提供虚拟设备模拟器，可注入丢帧、乱序、错误值和设备离线。

### 验收标准

- 无真实硬件也能通过 vcan 一键完成端到端演示。
- 协议解析包含边界值、非法帧和超时测试，核心逻辑测试覆盖率目标不低于 80%。
- 设备离线、恢复和错误帧不会导致节点崩溃或无限阻塞。
- 有总线负载估算，并能解释命令频率与状态频率的选择。
- ROS 2 层与底层协议解耦，可在不改协议核心的情况下替换消息接口。

## 阶段五：ros2_control 与控制基础（第 9–10 个月）

### 学习目标

- 理解 ros2_control 的 controller manager、hardware interface、resource manager 和控制器生命周期。
- 能为模拟或真实设备实现 hardware component。
- 掌握离散 PID、采样周期、饱和、抗积分饱和和低通滤波的基础。
- 理解位置、速度、力矩接口的区别，不追求高级控制算法。

### 具体技术栈

- ros2_control、controller_manager、hardware_interface。
- joint_state_broadcaster、position/velocity controller。
- URDF/xacro 的必要部分。
- PID、限幅、anti-windup、一阶低通；Python/NumPy 仅用于离线画图和参数分析。

### 项目交付：双轮底盘或双电机控制系统

在阶段四网关之上实现 ros2_control 硬件接口：

- 支持模拟后端，并尽量支持 CAN 后端。
- 导出位置/速度状态和速度命令接口。
- 实现基础 PID 或使用标准控制器完成速度闭环。
- 记录阶跃响应、稳态误差、超调、控制周期抖动和掉线后的安全行为。

### 验收标准

- controller manager 能正常加载、激活、停用控制器，状态切换无崩溃。
- 模拟后端可稳定运行；有硬件时，真实后端与模拟后端共用上层接口。
- 命令超时后进入明确的安全状态，例如速度归零。
- PID 调参有实验依据，能解释 P/I/D、饱和和采样周期对结果的影响。
- 形成 3–5 分钟演示视频或动图、完整 README、测试结果和性能报告。

## 阶段六：整合、作品集与面试准备（第 11–12 个月，机动）

该阶段用于补缺和整合，不强制在 10 个月主线后继续扩张技术范围。

### 学习目标

- 把前五阶段整理为一个可复现的代表项目。
- 将“使用过技术”转化为“解决过什么问题、如何验证”。
- 对目标岗位补齐常见 C++、Linux、网络和并发面试知识。

### 项目交付

- 一个主仓库：双轮底盘/设备控制系统。
- 一个独立性能仓库或子目录：DDS 与实时性 benchmark。
- 一份不超过 4 页的技术总结：架构、关键取舍、故障案例、性能结果。
- 简历中 2–3 条量化项目描述，每条都能对应代码、测试或实验数据。

### 验收标准

- 在全新环境按文档能完成构建与仿真演示。
- CI 至少执行编译、格式检查和核心单元测试。
- 能在 10 分钟内讲清数据链路、线程模型、故障处理和性能瓶颈。
- 能回答项目中 3 个真实故障的“现象—定位—修复—验证”全过程。
- 不以提交数量、代码行数或证书作为成果指标。

## 每周执行模板

常态每周安排可固定为：

- 2 次 × 2 小时：实现当周项目纵向切片。
- 1 次 × 2 小时：原理学习并立即做最小实验。
- 1 次 × 2 小时：测试、性能分析或故障注入。
- 1 次 × 2 小时：继续集成并解决阻塞问题。
- 1 次 × 1 小时：整理数据、文档和下周任务。
- 其余 1–5 小时：按项目风险分配，不用于无目标地刷课程。

每周只设一个可验收主目标，例如“完成 QoS 不兼容复现并写出抓包结论”，避免同时开启多个方向。若连续两周没有可运行交付，应缩小项目切片，而不是继续增加学习资料。

## 现有能力的迁移映射

| 现有能力 | 迁移到机器人系统软件 | 需要补齐 |
| --- | --- | --- |
| C++ 网络编程 | DDS 数据路径、SocketCAN、设备协议、性能诊断 | ROS 2 执行器、QoS、实时线程约束 |
| C++ 协程 | 理解异步任务、状态机和非阻塞 I/O | 不把协程直接放进硬实时路径；先掌握线程调度和边界 |
| Python | benchmark 驱动、数据分析、测试工具、设备模拟器 | 核心运行时和硬件接口坚持使用 C++ |
| ONNX C++ 部署 | 模型运行时集成、内存/延迟分析 | 暂不扩展模型训练；未来只作为感知组件接入 |
| OpenCV | 传感器数据处理和时间戳链路 | 暂不深挖视觉算法，重点观察数据吞吐与调度 |
| ROS 基础 | 快速进入 ROS 2 工程和工具链 | DDS、executor、lifecycle、ros2_control |
| ACM | 数据结构、边界处理、编码速度 | 工程分层、测试、可观测性、性能证据和长期维护 |
| Web 开发 | API 设计、配置、日志、CI、可视化界面 | 保留为调试面板或就业兜底，不继续追逐前端框架 |

Web 能力可用于制作轻量诊断面板，展示延迟、设备状态和错误计数，但面板只消费数据，不应成为主项目。建议限制在整合阶段的 1–2 周内完成。

## 考研冲刺降载规则

降载以时间窗口和学习结果为触发条件，不依赖临时意志：

1. 距离初试 9–12 个月：机器人主线保持每周 8–12 小时；不新增旁支项目。
2. 距离初试 6–9 个月：降至每周 4–6 小时，只完成当前阶段的最小闭环。
3. 距离初试 3–6 个月：降至每周 2 小时，限于修复、测试或文档，不引入新依赖和新硬件。
4. 距离初试不足 3 个月：默认暂停开发；每两周最多 1 小时做仓库健康检查，保持能构建即可。
5. 若考研周计划连续两周完成率低于 80%，机器人投入立即下调一级。
6. 若学校考试周、竞赛或身体状态冲突，优先暂停机器人项目，不用熬夜补工时。
7. 初试结束后先恢复到每周 6 小时，连续两周稳定后再回到常态投入。

降载时保留的优先级依次为：可构建 > 测试可运行 > 已有项目闭环 > 文档整理 > 新功能。暂停点必须记录“当前状态、下一步命令、已知问题”，降低恢复成本。

## 现在不学 / 不深挖

为保证主线收敛，未来 9–12 个月主动排除以下内容：

- 不深挖 SLAM、三维重建、点云算法、视觉大模型和模型训练。
- 不系统学习高级控制：MPC、LQR、鲁棒控制、强化学习控制仅了解名词和用途。
- 不同时学习 ROS 1 与 ROS 2；遗留 ROS 1 只在岗位明确要求时补迁移知识。
- 不遍历所有 DDS 实现，也不从头实现 DDS/RTPS 协议栈。
- 不追求硬实时认证、功能安全认证或自行维护实时内核。
- 不扩散到 EtherCAT、TSN、AUTOSAR、SOME/IP。CAN 主线完成后，仅按明确岗位需求选一个补充。
- 不购买大量硬件；在 vcan 和模拟后端未通过验收前，不用硬件掩盖软件问题。
- 不为了“技术先进”滥用无锁结构、协程、模板元编程或自研框架。
- 不继续堆 Web 框架、移动端、云原生和微服务课程；只维持已有能力。
- 不以刷完课程、收藏资料、获取证书代替项目交付。

## 路线完成后的岗位对应

优先投递：

- 机器人/智能汽车 C++ 中间件开发。
- ROS 2 平台、设备接入、通信与基础设施开发。
- Linux C++ 系统软件、车载通信或测试工具开发。
- 机器人控制软件工程岗位中偏工程实现、非算法研究的方向。

谨慎投递纯算法岗和要求深厚现代控制理论的岗位。筛选实习和校招 JD 时，优先匹配 C++、Linux、网络/总线、并发、ROS 2/DDS、性能调优和工程测试；若岗位主要要求论文、模型训练或高级控制，应视为另一条路线，不临时改主线。
