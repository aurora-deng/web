# NEBULA 全项目改进意见与实施对照

本页建议已获本轮实施授权；实际改动、真实验收和待具备条件的条目统一见[实施与验收清单](project-review-implementation-2026-11-19.md)。下文保留评审时的依据和建议，不能当成全部已经完成的声明。

日期：2026-11-19。用途：给你审阅、选择下一轮工作，不自动实施下面的新范围。当前埋点改动与验收单独记录在[业务埋点说明](../observability/business-instrumentation.md)。

## 1. 我的建议

下一轮先做“完整交付可复现”和“可复核的故障定位”，再做大规模平台扩展。保持 Linux 后端、Windows 私人客户端、浏览器前端的分工，继续冻结 `backend/server/`。现在没有证据支持重写通信核心、把所有服务微服务化，或者把 Observer 全部改写成 C++。

建议依次选择三件事：

1. **把交付档位与运行状态说准**：基础业务包和完整原生 AI 包各自需要什么，缺什么就明确报错；编译开关、实际运行模式和真实验收分开显示。
2. **完成一次闭环排障**：从“聊天 ACK 变慢”进入同窗指标、业务/数据库 Trace、日志与剖析，保存修复前后的对照证据。
3. **继续拆最集中的业务编排**：优先处理 `AiChatService`、`PostgresStore` 兼容层和 Observer 的查询路由，不再围绕已经很短的 `main.cpp` 反复重构。

## 5. 我最建议先做的三项

### 5.1 R1 + R2：让其他人能拿到同一个项目

把“可复现”做成三个明确档位：

- **通信档**：原 server 的协议、连接与调度测试，不引入业务依赖。
- **业务档**：账号、聊天、社区、PostgreSQL 和基础监控；可选 AI 关闭也能完整工作。
- **完整原生档**：在上层增加 gRPC/ONNX、TTS、MQ 等实际启用能力，列明 Worker、依赖、模型和资源预算。

每档分别输出源码/二进制摘要、功能开关、迁移版本、启动配置、实际执行测试和已跳过项目。不要把“ONNX 编译为 ON”当成“模型已加载并可生成”。

建议先完善现有 Python/CMake 入口，不急着再引入一套包管理器、容器编排或安装框架。已有依赖继续复用，新下载单独审批。

### 5.2 R4：围绕一次慢 ACK 建立作品主线

```text
发现聊天 ACK P99 上升
  → 核对样本量、错误率与采集是否连续
  → 查同窗服务端队列、连接池、COMMIT 与 ACK 就绪
  → 展开对应 Trace 和业务日志
  → 用 CPU/内存/I/O/syscall/调度剖析验证假设
  → 只改一个候选瓶颈
  → 同环境三轮对照并保存失败与恢复证据
```

Trace 像快递的过站扫描：告诉你在哪一段花了时间，不需要拆开包裹。连续剖析则解释这段时间里线程在执行、等待还是分配内存。两者要相互印证，不能只看一张 P99 图就决定重写 Reactor。

继续保留历史 ACK 尾延迟未达标和高噪声记录。数据库连接异常、强杀恢复和幂等重试已经有基础，下一步把它们串成可重复演示的中文排障流程，而不是再增加没有真实数据的面板。

### 5.3 R5 + R7：拆责任，保留接口

建议小步调整，保持现有功能调用关系：

```text
业务适配器
  → 应用服务
  → 领域规则 / Repository Port
  → 同事务的数据库实现与 Outbox
```

- AI：先分开“接纳与配额”“上下文准备”“生成终态与持久化”，保持取消和超时由同一个状态机裁决。
- Observer：把“请求校验、查询编排、数据源适配、页面渲染”分开，继续复用现有标准库服务。
- PostgreSQL：按账户、联系人、会话、消息等领域继续委托；跨模块写入通过工作单元协调，不让应用层直接接触 `PGconn*`。
- 前端：沿用组件初始化、订阅、销毁和统一 API 绑定。业务模块需要可协作，但不必机械追求前后端文件一一同名。

不建议一次性把所有文件移动一遍。每拆一块，就跑对应契约和真实服务回归，并记录调用图与回退点。

### 5.4 Windows 私人客户端：先验证边界，再扩 Agent

当前客户端组件已较小，`ProxyServer`、连接池、本地助手和存储有分工；没有依据再做一次大范围改目录。下一步把 R1、R10、R11 延伸到本地入口：

1. 验证 Linux 暂时断线、证书变化、代理中断、切号和退出后，旧请求不能继续写入新账号历史。
2. 录入一份专用测试资料，核对本地索引、请求片段、服务器消息库和日志；“文件留在本地”不能被错误宣传为“任何片段都不会送往推理服务器”。
3. 用既有资源采样测空闲、导入、检索和流式生成内存；200 MiB 仍应作为待实测目标，不能以代码较短替代测量。
4. Agent 确认卡绑定具体目标和载荷，重复确认沿用操作编号；模型不支持结构化工具时，继续退回问答和草稿。

优先复用现有 Boost、SQLite 和 Windows 凭据保护能力。没有真实需求前，不新增本地常驻模型或另一个后台框架。

### 5.5 聊天、神树和个人页：按用户旅程收尾

已有主题 Token、聊天消息控制、实时控制、会话控制等组件，当前较大的聊天控制器约 380–440 行；不应把它们概括为“前端完全没拆”。后续先验证同一用户操作如何穿过这些组件：

- **状态一致性**：发送后依赖真实 ACK；撤回、已读、搜索定位、补发和多端免打扰互相衔接，不让迟到响应恢复旧状态。
- **视觉与可访问性**：深浅主题、字体缩放、键盘焦点、错误提示和移动抽屉使用同一套规则；神树的装饰不遮住操作与文字。
- **资源有界**：长历史限制 DOM 和缓存；树后台停帧、移动降级，低配和 WebGL 不可用时列表功能完整。
- **权限可核对**：树故事、好友动态、仅自己可见内容和旧媒体地址分别验证；页面隐藏按钮不能替代服务器拒绝。

这一轮的重点是完整旅程和证据，不再为了“像另一个软件”重做一遍皮肤。测到的慢查询、重复渲染或资源泄漏，再进入有对照实验的优化。

## 6. 暂缓事项

- 不为“看起来企业级”立刻加入 k8s、服务网格或一堆新存储。
- 不用关闭 PostgreSQL 持久性、撤掉鉴权或跳过失败测试来改善数字。
- 不把 SQLite 在单机研发环境的使用直接判为错误；先测查询、写入、保留清理和并发等待。
- 不声称手工计时已经获得每个函数的精确 CPU 或内存；这需要适配的剖析方式与权限。
- 不继续扩大 `main.cpp` 的重构范围；当前入口已负责装配和顶层异常边界。
- 不把私有助手的资料、提示词、回答或长期记忆写入遥测；质量评估和失败重放需要独立授权路径。

## 7. 你审阅时可以直接给的意见

你可以按编号回复，例如：“先做 R1、R2、R4，R8 只接现有 Prometheus/Tempo；保持 server 冻结。”

我建议你重点决定：

1. 下一轮更看重“别人能部署复现”，还是“完整演示一次性能/故障定位”。
2. Observer 继续定位个人研发工具，还是准备给多个用户/多台机器使用。
3. 完整原生 AI 档是否作为下一次 GitHub 交付的正式验收范围。

确认后再把选中项排成下一阶段实施计划；本页不自动申请依赖、公开监控、修改原库或推送仓库。
