# M2 Skill 颗粒度与技能库 · 能力合同

P0 · S1 定合同，P1 扩接入。Skill 是一个可以说明开始条件、成功状态和失败后的处理方式的工序。

**当前与 M01 并行**。三个车队查询与提案 Skill 已登记为 v1，三份机器人侧合同映射到既有边缘实现。经批准的工单使用统一 `NavigationSkill` 端口，回执沿用边缘账本。本轮用软件模拟器验证了交接。 [查看 v1 合同与两侧边界](skills/README.md)

## 技术要求

| 字段 | 验证问题 |
|---|---|
| ID、版本、输入、输出 | 任务是否可在不改接口的情况下更换实现？字段缺失、版本不兼容时怎么报告？ |
| 前置与后置条件 | 开始和结束都能用观测或状态判断，条件过期时怎么拒绝？ |
| effect、冲突、权限 | 对状态、外部写入或物理动作有什么影响，谁能授权，哪些资源在一次执行内独占？ |
| deadline、取消、失败结果 | 是否有限期停止，超时后结果是否可查询，重试或补偿依据什么？ |
| 日志与测试替身 | 一条错误至少能查到版本、尝试、设备与可解释原因，合同与实现都能测试。 |

同一 Skill 可以有模拟、ROS 和设备适配实现。注册表记录各设备实际支持的 ID 与版本。目录固定后再扩展选择策略。

## 学习内容与目标深度

| 知识 | 达成的程度 |
|---|---|
| 颗粒度 | D2。能把「完成仓库任务」拆成可验收工序，说明共享资源和需要写在同一合同内的部分 |
| 版本与类型 | D3。用固定输入/输出契约及错误枚举做旧版兼容、版本拒绝、默认值检查 |
| 失败语义 | D3。区分暂时不可用、确定拒绝、需要人工处理、结果不明。能选拒绝、等待、重试或对账 |
| 可观察能力 | D3。对模拟和 ROS 实现复用同一组输入与断言 |

## 实施步骤

1. 选 3 个练习能力。 `GetRobotStatus` 查询本地状态，`NavigateToSimStation` 把机器人引向已登记模拟站点，`ReportTaskOutcome` 提交运行结果。每个能力独立写完成条件和所需证据。
2. 划分 effect。查询状态只读，登记结果是可按业务键去重的写入，导航有物理副作用，需要本地许可、取消和对账。用队列比较不同 effect 的重试策略。
3. 从静态注册表起步。运行时把 `skillId/version` 解析成固定适配器，边缘只公布实际启用的技能。A/B 或升级期间保留一个明确兼容窗口。
4. 用无硬件替身验证合同，给导航补前置状态、资源占用和超时。ROS 适配接相同合同，完成、失败和取消都产生事件。
5. 把三类技能嵌进 M4 的一张图和 M5 的两个模拟机器人，再从 M1 引入已审核的计划模块。

## 预期产出

一份版本化的三个 Skill 的合同、静态注册表设计、一份兼容和失败对照表、三套替身/ROS 共用断言。S1 初稿先覆盖这三个能力，P1 加设备适配。

## 验收标准

| 检验 | 通过条件 |
|---|---|
| 可独立判定 | 每条 Skill 至少有正常、前置不满足、超时、取消、重复报文五类测试 |
| 版本与身份 | 不支持版本/未知技能能在执行前发现，发生率可查询 |
| 资源冲突 | 两个需要同一底盘资源的任务同时到达时，有且只有一个占有执行资源 |
| 重试与对账 | 幂等写重复两次只有一次结果；物理动作的未知状态进入核实流程 |
| 可复用性 | 假实现替换为 ROS 适配，任务图、输入断言及记录字段可以复用 |

自测。把「转一圈采样」拆成目标运动和观测两项，分别判断哪个能力应该拥有控制资源，哪个能力应该产生数据证据。
