# M0 工程收口 · TSan、CI、Tag 与 Agent 位置

P0 · S0。目标是拿到一个能复验的 C++ 项目版本，并为下一步的 Agent 运行时划清边界。

## 技术要求

| 要求 | 交付标准 |
|---|---|
| 可复现版本 | 来源 SHA、Git 工作区状态、工具链、功能开关、依赖来源、已运行的测试与结果对应同一份记录 |
| 并发正确性 | 独立的 TSan 构建与执行记录，覆盖并发请求、取消、跨线程完成、关闭与资源回收 |
| CI | 可区分编译、运行、跳过和依赖失败，可信 runner 有清晰的入口与权限 |
| 版本标记 | annotated tag 指向经过核对的提交，标签注明测试范围与限制 |
| Agent 位置 | 浏览器继续负责交互，车队运行在独立 C++ 边界；冻结通信核心的检查继续生效 |

## 已有基础与待补能力

- **已有**。当前发布提交为 `ac2c1dd`。项目有 CMake configure/build/test 的 `tsan` preset、源码 CI、Linux 业务和原生打包工作流，以及通信核心文件摘要检查。工作区包含发布之后的安全与运维改动，按来源分批核对。
- **本阶段结果**。原生 TSan 和 ASan/UBSan 已复验，CI 增加独立 C++ 与 sanitizer 档。预编译 gRPC/Abseil 的全链路 TSan 诊断仍保留。版本可用本地复现快照和源码摘要定位。 [C++ 验收记录](../../ops/validation/cpp-systems.md) · [CI](../../../.github/workflows/ci.yml) · [历史 TSan 证据](../../observability/validation.md)

## 学习内容与目标深度

| 学习项 | 具体掌握程度 |
|---|---|
| TSan 与内存模型 | **D3**。用 happens-before 解释两段访问为何相撞，区分数据竞争、生命周期错误与工具不支持。能根据堆栈找对象所有者和锁。 |
| Git 与发布证据 | **D3**。区分分支、提交、annotated tag 和 Release，能用独立检出核对同一个版本。 |
| CI | **D3**，进阶 D4。会用小型矩阵和受控执行器，能复查测试发现数、退出码、超时、工件保留和最小权限。 |
| Agent 边界 | **D3**。能画出浏览器、会话服务、模型 provider、DAG 与车队协调器的依赖，并指出跨层实现放在哪里。 |

TSan 像带录像的交叉路口，在实际走过的线程路径上检查有冲突的访问。用例覆盖决定能看到多少路口。首先读官方工具说明，再拿本项目的取消、数据库任务与停止路径解释一份真实报告。[LLVM ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html) · [Git 标签](https://git-scm.com/docs/git-tag)

## 实施步骤

1. **盘点工作区与证据**。列出 `git status`、`git diff --stat`、`git tag --list` 和发布 SHA。根据业务安全、网关、运维和文档变更分组，保留作者、用途和验证状态。现有的原始实验数据按大小、用途和内容分类，归档保留摘要与取回方式。
2. **先复现现有路径**。在隔离检出执行源码检查、一个受控 CTest 和一个历史故障实验。保存运行日期、构建器、工具链、fixture 版本与退出码，确认用例实际执行。[现有复现操作](../../ops/validation/reproduce.md)
3. **打通 TSan 链路**。确认 Linux 的编译器与运行库来自同一可用工具链，使用已有 `cmake --preset tsan`、`cmake --build --preset tsan`、`ctest --preset tsan`。先做工具链冒烟，再跑 worker 并发、deadline/cancel、close/shutdown。首个报告保存测试名单和原始摘要。若出现环境阻塞，记录缺失的库、失败阶段和已执行用例数。依赖变更走已有审批流程。
4. **补 CI 最小工作流**。PR 使用快速源码与现有测试门禁。隔离 Linux 的可信触发运行 TSan 和 ASan/UBSan，各有独立构建目录、超时和报告。先验证一次受控运行与失败可见性，再判断哪些用例适合成为必要检查。保留 Linux 业务和 Windows 兼容检查的差异。
5. **形成发布锚点**。从已复验的提交决定版本名，先查询同名标签，再在未来发布步骤使用 `git tag -a <版本名> <已验证提交>`，注释附构建入口和验收范围。发布审核逐项核对 SHA、测试、工件摘要和回退入口。
6. **写 Agent 位置决策**。通用运行时独立在 `backend/workflow/`。后续 `backend/agent/planning/` 可装配模型端口、业务端口与车队协议适配。先验收通用执行与车队工单。 [架构与目录](architecture.md)

## 预期产出

一份版本和证据对照表、一份可复跑的 CTest/TSan 记录、一份 CI 运行说明、一页发布和回退步骤、一项 Agent 放置决策。S0 预留 14–22 小时。

## 验收标准

| 检验 | 通过条件 |
|---|---|
| 检出复验 | 两次独立检出的 SHA、配置和成功用例可对应，失败能定位到阶段 |
| TSan | 有工具版本、测试数、退出码和覆盖表。候选声明“覆盖项通过”时须有可运行的并发用例与零未处置报告。第三方已确认项需有成因、范围与复查记录 |
| 环境阻塞 | 单列 BLOCKED，保留日志；允许进入纯模拟学习，发布记录继续标注未验覆盖 |
| CI | 有一次真实通过与一次可解释的控制失败，空用例或缺失产物不能被记录为通过 |
| Tag/边界 | 标签可定位到证据提交，候选依赖满足冻结检查，原始业务与日志证据可追溯 |

自测。拿到一次「检测器在回收对象时报警」的报告，先说哪两个线程持有这个对象，再解释日志、编译和运行证据各能说明什么。
