## 一、求职与项目定位

**先做一份 C++ 系统作品，再让它调度 ROS 2 机器人。** 作品的主线是 C++ 并发调度、gRPC 控制面、断线恢复、事务与运行证据。你想做的母 Agent 放在调度之上，负责读数据、提出任务和总结失败。每台机器人的子 Agent 承接任务，导航、感知和执行器作为分工明确的能力模块。本体继续拥有运动许可和停机权。

| 优先级 | 目标岗位 | 用 NEBULA 证明什么 |
|---|---|---|
| 优先投递 | C++ 系统研发、网络与中间件、分布式基础设施 | 独立编写调度与通信组件，解释生命周期、竞态、背压、重放、P99 和失效边界 |
| 主攻发展 | 机器人软件平台、ROS 2 中间件、车队调度、机器人数据基础设施 | 将相同控制协议接入机器人进程，复现断连、恢复对账、时间漂移和本体安全拒绝 |
| 差异化积累 | Agent 平台、AI Native 工具编排、具身模型部署 | 结构化计划、可版本化 Skill、权限仲裁、模型超时降级和可重放评估 |
| 后续拓展 | 端侧推理、运动控制、策略学习与 HIL | 可测的设备接口、数据集质量和控制时序，按设备条件逐级验证 |

招聘样本支持将 Linux、C++、并发与工程验证放在最前。ROS 2/DDS、传感器数据、仿真与实机联调在机器人软件岗位更集中，PyTorch、策略训练和端侧加速在模型与部署岗更重要。岗位职责和年限按各自职位查看。[官方招聘样本与技术优先级](job-market.md)

## 三、每阶段交什么

可直接查看 [当前 C++ 组件](../../architecture/overview/cpp-systems.md) 和 [运行与验收](../../ops/validation/cpp-systems.md)。下表继续作为长期阶段门槛。

工时是首版交付估算，包含学习、实现、测试和复盘。每周投入项目 10 小时，求职版约 **10–14 周**，单机 ROS 仿真版累计约 **13–18 周**。附件覆盖的完整研发路线按数百小时规划，逐模块门槛达成后再加范围。

| 顺序 | 投入 | 并行工作 | 通过条件与作品 |
|---|---:|---|---|
| **S0 工程收口** | 14–22 h | M0；给 M7/M12 整理证据与安全边界 | **G0**。版本和配置可定位；已有构建入口可从干净检出复验；TSan 有实际结果或明确工具链阻塞，单列受影响覆盖；记录 Agent 放置决策和发布顺序。 |
| **S1 C++ 调度内核** | 32–46 h | M4；M2 先写 3 个技能的契约；M7/M11/M12/M13 定事件、时钟、安全和故障夹具 | **G1**。无浏览器依赖的进程跑通含分叉/汇合的 5 节点图，覆盖取消、超时、限流；输出同一运行的状态、事件和可复跑基准。 |
| **S2 跨进程调度** | 48–66 h | M6 双向流与 M5 租约；M7/M11/M12/M13 的最小联调覆盖 | **G2**。1 个协调器和 2 个独立程序模拟机器人，任务可分配、失联可控、重连可核账；ACK 丢失和旧持有者结果有可重复证据。这个阶段就可以整理 C++ 岗作品。 |
| **S3 ROS 2 仿真与回放** | 28–40 h | M8 的单机 ROS 适配、M13 的场景、M7 的记录定位 | **G3**。一台 ROS 2 仿真机器人完成任务、取消、回报，与其他模拟机器人并存；用固定录包和种子复现一次状态或网络异常。 |
| **S4 Agent 辅助与真机准入** | 两条线单独验收 | M1/M2 做离线提案原型约 20–30 h；具备合适设施时，M8/M9/M10/M12/M13 的首轮实机验证约 45–80 h | **G4**。提案经审核，模型缺席时系统可运行。实机路线另核对本地安全、台架和低速准入矩阵，可与离线提案并行。 |
| **S5 数据、模型与规模化** | 按完成后的瓶颈重新估算 | M3 策略闭环、M10 多实体、M11 真跨机时钟、M13 HIL 及可选冷备 | **G5**。有可追溯的训练/评测/部署证据或真实多机运维证据，分别按对应模块验收。 |

每周 6 小时，G2 约需 16–23 周。每周 20 小时，G2 约需 5–7 周。先把 G0、G1、G2 写进周计划，再按实测速率改排期。考试周或工作繁忙时，安排可中断的 C++ 题、证据整理和设计复核，联调放在能保留整块时间的周末。

## 五、先做哪几件事

1. **把就业项目定稿到可讲**。用本地 Tag 定位 C++ 实验，选一个有日志和 Trace 的故障，从请求到事务按因果讲清。分别说明原生 TSan 已通过的覆盖、完整 gRPC 的待复核诊断和 CI 的执行状态。已有基准的噪声结论继续沿用原口径。
2. **写下五节点任务与失败表**。按节点就绪、取消、失效结果、完成上报写出预期，再按 M4 实现。先用已有同步接口跑通小图，线程或协程的复杂度等实测定位后引入。
3. **做两个脱离浏览器的本地进程**。一次成功提交、一次 ACK 丢失、一次执行者重启。运行证据同时保存版本、参数、时间窗、断言和 Trace 链接。
4. **把机器人能力接在同一张图上**。先用仿真实现替换一个适配器，保留任务和回报契约。一台可解释的机器人跑通后扩展第二台。

保底投递材料至少准备一张架构图、一份可复验的故障记录、一组带采样量的性能数据和一张决策表。每周可以把 2 小时用于现代 C++、Linux、网络和数据结构面试题，用当周真实问题写一页复盘。达到 G2 后，用同一版本分别准备 C++ 系统与机器人软件两份表述。

## 六、对附件取舍的记录

参考了《00-总学习方案》《NEBULA 架构演进规划》及 M0–M13 指导。保留模块划分、D1–D4、工程优先、母子分层和留证据的原则。本方案的首版工时按阶段重新计算，设备情况来自待盘点项。

| 讨论点 | 本方案采用的验收口径 |
|---|---|
| 版本、CI 和 TSan | 以可复现提交和有人能读懂的标签注释为交付；区分已运行、已失败和环境阻塞；报告保留覆盖与退出码。 |
| Agent 位置与协程 | 现有小研继续发挥会话价值，车队任务在独立 C++ 运行域接入。先迁移执行语义，协程和性能优化依据实际瓶颈。 |
| 安全、时钟和仿真 | 在 S1 定义最小契约，S2 就演练故障，之后补跨设备时钟质量、HIL 和真机门禁。 |
| 多台设备与模型 | 逻辑实例、真实多机、混合现场联调和 HIL 分别留证。训练在数据闭环建好后进入独立阶段。 |
