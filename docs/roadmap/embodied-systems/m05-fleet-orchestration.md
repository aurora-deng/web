# M5 分布式调度指挥 · 租约、幂等与对账

P0 · S2。实现一处可追溯的车队调度权威，两个独立边缘进程执行同样的任务合同。母 Agent 的建议在这个系统上方接入。

## 技术要求

- 机器人用能力、空闲/健康状态、新鲜度和资源约束进入候选集合。首个策略可用「满足约束且载荷最低，按稳定 ID 打破并列」。
- 持久化任务、分配、派发意图、租约和尝试。以单个持久化协调器为首版调度权威，租约代号随更换递增。
- 边缘独立处理接收、执行、回报、失联与恢复。命令 ID 跨重试稳定，身份验证与本地安全门在执行前再次检查。
- 对账明确出现过的失效回报、已执行但未上传、只接收、已取消与结果不明。位置与资源释放需要边缘可信状态。

## 已有基础与待补能力

- **已有**。NEBULA 有 PostgreSQL、事务 Outbox 与历史双实例故障证据；前端协作示例可生成合成观测与待确认提案。[双实例验收](../../observability/validation.md#双实例实时投递与告警验收) · [协作示例](../../../examples/agent-coordination.mjs)
- **本轮**。协调器和边缘持有各自的 SQLite 账本，按能力选择可领取工单，保留派发代号、接收和结果。网络断开后保留原占有，先重放回执，再按需要对账。两个和三个软件边缘使用固定负载采样。独立协调器仍是实验的调度权威。 [本轮压测与故障复验](../../ops/validation/m00-m07.md) · [旧版跨机证据](../../ops/validation/cpp-systems-cross-vm.md)

## 学习内容与目标深度

| 知识 | 达到的程度 |
|---|---|
| 事务、幂等与发件箱 | D3。能画出数据库提交、消息发送与回执三个断点，说明重跑何时无害 |
| 租约与 fencing token | D3。租约像有期限的领单权，代号像交接编号。能说明过期回复为何无权提交 |
| 重连对账 | D3。用两个账本核对同一命令，能分清确定失败、已经执行与待人工核实 |
| 策略、容量与 HA | 进阶 D4。能给出公平性与热点证据，解释单协调器、冷备和多领导者各自的复杂度 |

## 实施步骤

1. 让两个模拟边缘进程登记能力，通过固定策略执行工单。用相同输入获得相同分配结果，记录每次选择原因。
2. 在同一事务写入占有与派发记录，事务完成后发送。每台机器人保存已接收命令和本地状态；回报先区分接受、执行与结束。
3. 执行者更换时更新 fencing token。旧 Worker 的迟到回报进入可审计拒绝，当前本体是否仍在运动由本地约束和对账确认。
4. 重连时交换最新租约、活动命令及完成摘要。优先回补结果，未知动作先查询本地状态。允许边缘在已批准且仍然安全的有限范围内处理正在进行的任务。分区中保持操作窗口可见。
5. 演练确认丢失、协调器与边缘进程重启、排队过载及过期回报。再接真正 ROS 适配器。优先级与抢占按可取消技能交接验证，冷备另外评审 fencing 的权威来源。

## 预期产出

1 个协调器 + 2 个边缘进程的可复跑实验，配套状态图、调度记录、两份账本样例和埋点。G2 就能讲清「复用事务与异步通信，处理分布式副作用」。

## 验收标准

| 场景 | 断言 |
|---|---|
| 能力与互斥 | 准备 30 张含不同能力约束的工单；每张可用工单只有一个有效占有，忙碌资源不会再领冲突任务 |
| 确认丢失 | 发送后切断回执；恢复账本得到已处理或对账中，等效动作最多一次 |
| 协调器重启 | 进程退出再启动，同一任务重建可见状态，旧代号结果被拒绝，保留 Trace |
| 失联与状态不明 | 机器人保持或进入本地安全态，协调器显示待对账；重新派发之前可证明安全条件和控制权已满足 |
| 扩展 | 先在同一主机跑两个进程的功能回归，再用固定负载记录 2、3 个逻辑机器人时的 ACK 延迟、队列、CPU/RSS 与失败类型 |

自测。如果协调器崩溃时 A 已经移动，数据库仍显示「已派发」，如何从接收记录、现场状态和代号判断是否能把同一资源交给 B。
